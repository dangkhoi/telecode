Phase A — Bug fixes + quick wins

Context

The v1.0 streaming pipeline forwards adapter AgentEvents to the Telegram dispatcher inside src/bot/commands/index.ts. The dispatcher routes per-event:

  • text → notifier.appendStream(key, chunk, { silent: true }) with 3-second debounce + edit-message rotation.
  • tool_use → one sendPlain per event, with the raw input JSON pasted into the message and a follow-up suggestion keyboard attached immediately.
  • error, done → live + push notification, drain any background buffer first.
  • tool_result, status, session → silently ignored (no dispatch branch).

Plan §1 (Bugs & pain points) flagged two real defects + three friendly-render gaps that don’t need the bigger Phase B mode system to fix. Phase A ships those without touching dispatch architecture, so it can land independently and remains 100% backward-compatible (verbose users see the same rate of events; only the rendering differs).

A.1 — Claude tool_use de-duplication

Context

v1.0 src/agents/claude.ts emitted {type: 'tool_use'} from two places:

  • canUseTool callback at line 55 — fired by the SDK’s policy gate.
  • PreToolUse hook at line 108 — fired after the SDK approves and is about to invoke the tool.

For every Claude tool call, Telegram saw two announcements. The Codex + Cursor adapters never had this bug because they emit from a single point.

Decision

Drop the canUseTool emit. canUseTool is a policy gate (approve/deny) and should not announce; the PreToolUse hook fires after the policy decision and is the correct moment for user-facing notification. This is the lighter-touch fix — removing the line preserves the SDK’s contract (the hook is the SDK’s canonical pre-call surface).

Side effects preserved: policy bookkeeping (store.logTool, store.updateSession) still runs inside canUseTool. Only the user-facing emit is removed.

File Changes

  • src/agents/claude.ts — remove start.onEvent({ type: 'tool_use', ... }) from the decision === 'allow' branch of canUseTool (former line 55). Replace with a comment that explains why this point is intentionally silent.
  • tests/claude-tool-use-dedup.test.ts — new. Mocks @anthropic-ai/claude-agent-sdk.query to capture both the canUseTool and the PreToolUse hook the adapter wires, then invokes both for a single tool call and asserts the adapter emits exactly one tool_use event.

Verification

  • Unit: claude-tool-use-dedup.test.ts × 1 passes.
  • Full suite: 482/2 skipped (was 435/2 + 47 new).
  • Manual smoke (deferred to Phase A ship): run a real Claude session, fire a Read tool, observe a single 🔧 Read · ... message in Telegram.

A.2 — Surface tool_result events

Context

The AgentEvent union already includes {type: 'tool_result'; tool: string; ok: boolean; preview?: string}. Codex (codex.ts:435-451) and Cursor (cursor.ts:483-507) emit them when commands complete. The dispatcher branch in commands/index.ts only handled text | tool_use | error | done | session — tool_result fell through silently. Result: user never saw whether a Bash command succeeded or what its exit was.

Decision

  • Add a tool_result branch in dispatch. Render line: {icon} {tool} {label}{preview} where icon is ✅ for ok, ❌ for failure, and preview (already 240-char-bounded by the adapter) is folded into the next line.
  • Correlate with a previously-emitted tool_use via the per-dispatch PendingTools queue (A.5). On match: edit the original message in place via editMessageText, merging use + result into one block. This halves Telegram message count and visually pairs the cause with the effect.
  • Orphan tool_result (no matching pending entry — e.g. tool_use never reached us, or A.5 defer already fired): send a fresh sendPlain so the outcome is still surfaced. Never silently drop.
  • Background sessions: buffer the result line (type: 'tool_use') so catch-up still shows it when the user switches in.
  • No mode filter yet — that lives in Phase B. Phase A renders every result.

File Changes

  • src/bot/commands/index.ts — new else if (e.type === 'tool_result') branch under the dispatch onEvent. Active path edits via notifier.editPlain; orphan path falls back to sendPlain; background path appends to the per-session output buffer.
  • src/bot/notifier.ts — new editPlain(messageId, text, extra?) + editReplyMarkup(messageId, markup?) methods. Both wrap the corresponding bot.api.editMessage* with the token bucket + the same “message is not modified” tolerance pattern used by the streaming flush path.
  • tests/tool-result-dispatch.test.ts — 7 cases (orphan, merge happy path, ok=false, background buffered, defer fallback, done clears tracker, deferred suggestion attaches).

Verification

  • Unit: tool-result-dispatch.test.ts × 7 passes.
  • The AgentEvent type union was sufficient as-is; no extension required. Adapter shape { type: 'tool_result'; tool; ok; preview? } matches both Codex and Cursor emitters — verified by reading the adapter sources before implementing the dispatch branch.

A.3 — Strip ANSI for Codex bash output

Context

Codex emits command/exec/outputDelta notifications carrying base64-encoded stdout/stderr from the user’s shell command. v1.0 base64-decoded the delta and forwarded the raw bytes as a text event — ANSI escape codes (colours from cargo/pytest/npm, spinner show/hide from ora) survived into Telegram as \x1b[31mfailed\x1b[0m garbage.

The Kiro adapter (kiro.ts) already had a stripAnsi helper that worked correctly. The fix is to share that helper.

Decision

  • Extract stripAnsi into a new pure module src/util/ansi.ts with both regex patterns (SGR + cursor show/hide) exposed via _internals for tests.
  • Kiro imports the shared helper (behaviour unchanged).
  • Codex’s command/exec/outputDelta handler applies stripAnsi after base64 decode, before emitting the text event.

File Changes

  • src/util/ansi.ts — new. stripAnsi(s: string): string + _internals with the underlying regexes. Heavily commented so future contributors know it’s not exhaustive (no OSC/DCS support — add when needed).
  • src/agents/kiro.ts — replace inline ANSI_RE + CURSOR_HIDE_SHOW_RE + local stripAnsi with import { stripAnsi } from '../util/ansi.js'. Behaviour identical (same regex source).
  • src/agents/codex.ts — import stripAnsi + apply inside command/exec/outputDelta handler.
  • tests/ansi.test.ts — 6 snapshot cases.

Verification

  • Unit: ansi.test.ts × 6 passes.
  • Kiro behaviour preserved: existing kiro.test.ts (which inlines the same helper for its own assertions) continues to pass — we did not migrate that file’s internal copy because the test asserts the regex behaviour directly, not the import path.

A.4 — Friendly tool render

Context

v1.0 dispatch rendered tool calls as 🔧 {tool} — {JSON.stringify(input).slice(0,200)}. Result on Telegram:

🔧 Read — {"file_path":"/Users//Documents/workspaces/telecode/src/bot/notifier.ts"}

Plan §1.2 #2-3 flagged this as a top pain point: raw JSON noise + absolute paths that don’t collapse to a phone-readable form.

Decision

  • New pure module src/bot/tool-render.ts exports two functions:
    • renderToolUse(toolName, input, ctx?) — per-tool friendly line (Read · basename, Bash · cmd[80], Grep "pat" in path, Glob pattern, Write · basename (size), etc.). Multi-adapter aliases (Claude/Cursor PascalCase + Kiro/Codex snake/dotted forms) all collapse to one rendering.
    • collapsePath(absPath, projectCwd?) — three-step collapse: project cwd → ./relative, else home → ~/relative, else absolute. Length guard at 50 chars falls back to …/<last-2-segments>.
  • Cross-platform: uses node:path + os.homedir(), no hardcoded /. Tests cover Linux/macOS absolute paths; Windows drive-letter is supported via the same path.isAbsolute / path.relative path (no platform fork inside the helper).
  • Dispatch wires it: tool_use branch composes 🔧 {renderToolUse(...)} instead of the raw-JSON slice. Suggestion keyboard moved to A.5 (deferred to tool_result).

File Changes

  • src/bot/tool-render.ts — new. ~210 LoC with heavy commentary on heuristics + the path-collapsing length guard.
  • src/bot/commands/index.ts — import { renderToolUse }; tool_use branch composes line via the helper, passing the session’s project cwd as projectCwd for relative collapsing.
  • tests/tool-render.test.ts — 21 cases covering per-tool, multi-adapter aliases, fallback, all path-collapsing rules.
  • tests/session-gating.test.ts — updated 2 assertions that asserted the v1.0 raw-JSON shape (/^\[A\] 🔧 Bash — /) to match the v1.1 friendly shape (/^\[A\] 🔧 Bash · /).

Verification

  • Unit: tool-render.test.ts × 21 passes.
  • Integration: dispatch composes the friendly line correctly, verified in tool-result-dispatch.test.ts (asserts "🔧 Bash · ls" appears in merged messages).

A.5 — Suggestion keyboard suppression

Context

v1.0 attached the follow-up suggestion keyboard ([▶️ Tiếp tục] [🔁 Run again] [↩️ Rollback]) at the moment tool_use fired — before the user could possibly know whether the call succeeded. The buttons looked premature ("Continue… from a failed thing? Run-again before knowing it ran?"). With A.2 now surfacing tool_result, the keyboard belongs on the result, not the use.

Decision

  • New helper module src/bot/pending-tools.ts — per-dispatch queue of pending tool_use messages, keyed by tool name (LIFO match because no adapter threads a stable call-id end-to-end).
  • Dispatch tool_use: send the message WITHOUT a reply_markup, register a pending entry, start a 2-second defer timer.
  • Dispatch tool_result: resolve(toolName), cancel the timer, edit the original message in place adding both the result line and the suggestion keyboard (one round trip via editMessageText with reply_markup).
  • Adapters that never emit tool_result (currently Claude — deferred fix): the 2-second timer fires onTimeout, which retrofits the suggestion keyboard onto the original message via editMessageReplyMarkup. Preserves the v1.0 affordance exactly so the regression footprint is zero.
  • done event clears the pending tracker — orphan defer timers can’t fire after the dispatch window closed.

File Changes

  • src/bot/pending-tools.ts — new. ~130 LoC pure helper. add / resolve / clear / size + onTimeout callback. No grammY/SDK imports — trivial to unit test.
  • src/bot/commands/index.ts — instantiate one PendingTools per dispatch, wire into tool_use + tool_result + done branches.
  • src/bot/notifier.ts — editReplyMarkup + editPlain helpers (also used by A.2).
  • tests/pending-tools.test.ts — 6 cases (add, LIFO resolve, no match, defer fires, resolve cancels timer, clear, callback that throws).
  • tests/tool-result-dispatch.test.ts — 7 cases incl. the “2s defer fallback retrofits keyboard” and “done clears pending tracker” scenarios.

Verification

  • Unit: pending-tools.test.ts × 6 + relevant cases in tool-result-dispatch.test.ts.
  • Backward compat: any session whose adapter still doesn’t emit tool_result (Claude) shows the keyboard after a 2-second delay — same behaviour as v1.0 from the user’s perspective, just timing-shifted by 2s.

Phase B — Mode system

Context

v1.0 streamed every adapter AgentEvent to Telegram with no mode awareness — great for debugging on desktop, noisy on phones. Plan §2.1 split the user base into four personas with very different signal/noise needs:

PersonaBucketNeeds to see
On-the-go (phone, glance)~50%approval + done + errors only
Casual monitor (phone, parallel)~30%+ tool calls + results compact
Focused (desktop, watching)~15%+ thinking + text response + status
Debugging (desktop, troubleshoot)~5%+ raw chunks + status (v1.0 firehose)

Phase B introduces four mode tiers (summary / normal / thinking / verbose) per-session, falling back to a per-chat default, then a baked-in default of summary. The dispatch handler now filters events through {@link shouldEmit} before routing into the notifier or buffer paths from Phase A. Default = summary is a behaviour change for v1.0 power users; mitigated by the v1.1 boot announcement (§B.5).

Design Decisions

D1 — Two-table storage (sessions.verbosity_mode + chat_settings)

Per-session override lives in sessions.verbosity_mode TEXT NULL (nullable — null means "use chat default"). Per-chat default lives in a new chat_settings(chat_id PRIMARY KEY, default_mode TEXT NOT NULL DEFAULT 'summary') table. Two tables, not one, because:

  • Migration story: an existing v1.0 DB gets verbosity_mode added via PRAGMA-guarded ALTER (idempotent, same pattern as Phase A's handoff_context). A separate table lets new chat-level settings (theme, language, summary cost cap) land later without touching sessions.
  • Migration-message bookkeeping: §B.5 uses "chat_settings has NO row yet" as the v1.1 first-boot marker. Coupling chat-default storage to the existence of the row gives us a free, deterministic "have we shown the announcement?" probe without a dedicated flag column.
  • Resolver simplicity: resolveMode(sessionMode, chatDefault) stays a 3-line pure function (session ?? chat ?? 'summary') instead of conditional joins.

D2 — Resolved-mode cache invalidated by command + chat-setting callbacks

Dispatch resolves the effective mode ONCE per turn (store.getSessionMode → store.getChatDefaultMode → 'summary') and stores it in a module-level Map<sessionId, VerbosityMode>. The cache:

  • Eliminates SQLite reads from the per-event hot path (a Bash tool_result burst can be hundreds of events/turn).
  • Stays consistent during a turn (no half-mode behaviour mid-stream).
  • Honours mid-turn /mode changes on the next dispatch (we invalidate at the callback site). A user that wants effect this turn can /stop first — an explicit, predictable trade-off vs the complexity of re-resolving per event.
  • /settings mode <name> blast-radius-invalidates every cached entry for sessions in the chat — broader scope, broader wipe.

D3 — Filter matrix lives in `shouldEmit` (one source of truth)

Per plan §B.4. The dispatcher pre-emits an early if (!shouldEmit(e, currentMode)) return guard; all event-type branches downstream keep their v1.0/Phase A semantics. Critical events (error, done, session) ALWAYS pass through — baked into the function, not the caller — so future additions can't accidentally suppress them by adding a case to a different branch.

Failure-on-send is logged + skipped (announcement is informative, not critical).

C.1 — MarkdownV2 helpers

File: src/bot/markdown.ts (new)

  • escapeMd(s): two-pass escape. Pass 1 escapes backslashes (so pass 2's added backslashes don't get re-escaped); pass 2 prepends \ to every spec-mandated special.
  • codeBlock(content, lang?): wraps in ```lang\n{content}\n```. Inside the fence we escape ONLY backticks + backslashes per spec; MarkdownV2 specials like dots and brackets are literal. The lang slug is sanitised (strip ` + newlines) as defence-in-depth against fence-breakout via malformed tag.
  • inlineCode(s): single-backtick span. Same backtick+backslash escape as code fences.
  • bold / italic / strikethrough: wrappers that compose escapeMd for inner content. *x* / _x_ / ~x~ form.

Design decision — regex character class: initial implementation used [_*\[\]()~`>#+\-=|{}.!] as a single character class, which treats +-= as a RANGE (ASCII 43–61 covers digits, commas, dots, slashes — mangling innocent text). Fixed by switching to an alternation form (\_ | \* | \[ | …) compiled once at module load. Caught by a "preserves non-special characters verbatim" test.

Test count: 27 cases in tests/markdown.test.ts — covers every spec special, adversarial inputs (all-specials, embedded triple-backticks, Vietnamese + emoji + ZWJ + RTL marks), wrapper composition, empty/null defensive paths.

C.2 — Auto code-fence detection

File: src/bot/code-fence.ts (new)

  • detectCodeBlock(text): returns { lang, isCode: true } | null. Heuristics applied in order of specificity:
    1. JSON — {…} or […] outer brackets AND contains a quoted-key pattern "…":. Rejects inline blurbs like "user said {hello}" (no quoted key) and bare numeric arrays.
    2. Diff — ≥ 2 lines starting with + or - at column 0 AND a hunk header (@@…@@) or file header (---  / +++ ). Both conditions required — markdown bullet lists don't trigger.
    3. Shell transcript — ≥ 2 lines starting with $  or > . Leading space mandatory so $variable doesn't trigger.
    4. Stack trace — ≥ 2 lines matching /^\s+at [A-Za-z_$<]/. Covers Node and JVM styles. Returns lang: null (no syntax highlighter for "stack trace" universally available).
    5. Generic monospace fallback — text > 200 chars AND has newline AND shows alignment cues (2+ indented lines OR 2+ runs of 3+ consecutive spaces). Returns lang: null.
  • maybeWrapCodeBlock(text): convenience wrapper that returns either fenced MarkdownV2 (on detection) or the original text unchanged (caller decides whether to escape further).

Design decision — conservative thresholds: every heuristic uses ≥ 2 markers instead of ≥ 1. Rationale: false positives (wrapping prose in ```) make the message uglier; false negatives (missing a snippet) leave it unchanged. Plan §C.2 calls this out explicitly — we err on the side of "leave alone unless markers are strong."

Performance: ~5 short regexes per call, all module-level globals. No matchAll allocations — we use a local countMatches that increments a counter via exec(). Safe to call per text event in the streaming hot path.

Test count: 19 cases in tests/code-fence.test.ts — per-heuristic happy paths + negative cases (inline curly braces, single +/- bullet, naked $HOME reference, short text with newline, long flowing prose without alignment) + defensive (empty / whitespace / non-string).

C.3 — Diff stats for Edit tool

Files: src/bot/tool-render.ts (extend) + src/bot/diff-cache.ts (new)

  • renderToolUse extension: when input carries both old_string + new_string (Claude Edit, Codex apply_patch, Kiro fs_write, also oldString/newString camelCase variants), the renderer appends (-X +Y) with X = old.split('\n').length, Y = new.split('\n').length.     No global timer — sweep is opportunistic on writes. Avoids the "setInterval pinning the process alive" issue.

    --- a/foo.ts
+++ b/foo.ts
-old line
+new line

C.4 — Collapse repeated tool calls

File: src/bot/tool-collapse.ts (new)

  • ToolCollapseManager: per-session burst collapser. Internal state: Map<sessionId::toolName, { msgId, count, items, firstSeenAt, lastSeenAt }>. Key includes sessionId for race isolation.
  • handle(sessionId, toolName, item, prefix) → CollapseAction: discriminated union { action: 'send' | 'edit', … }. Dispatcher acts on the result; manager itself never touches Telegram API.
    • First emit for (session, tool) → 'send', count=1.
    • Subsequent emit within 5s window → 'edit' on the recorded msgId, count incremented, items appended.
    • Tool switch for same session → previous entry finalized (forgotten); fresh send.
    • 5s+ elapsed → fresh send, count reset.
  • recordSent(key, msgId): dispatcher calls after sendPlain resolves. recordSent(key, null) tears down so we don't try to edit a phantom message after a send failure.
  • Items truncation: when concatenated items exceed maxDisplayChars (default 80), keeps newest items + prepends "…". Newest-first because debugging usually cares about the freshest file names.
  • Background sweep: 60s interval (configurable), evicts entries past window. Timer is unref'd so it doesn't pin the Node process alive on a quiet daemon.
  • clearSession(sessionId): drops all entries for the session in O(M) where M is shard size. Called by session-close handler.
  • stop(): shuts down the sweep timer cleanly. Idempotent. Called on daemon shutdown.

Design decision — pure utility, no Telegram coupling: the manager returns "what to do" (send/edit + formatted text + key), not "do it." Lets the dispatcher reuse the existing notifier.sendPlain / notifier.editPlain path with its rate limiting, scrubbing, and 429 handling intact. C.5 — Path collapsing enhance (git-root + Windows)

Phase D — Agentic compression

Context

Phase A surfaced tool_result events. Phase B added mode-aware filtering. Phase C wrapped structured text in code fences and collapsed bursts. None of those touched the most expensive UX failure mode of v1.0: raw 200-line bash output dropped verbatim into Telegram. Rule-based truncation (the preview.slice(0, 240) path) loses the meaningful signal — the test count, the failure file, the deprecation warning — and keeps the noise.

Phase D inverts the relationship: instead of telecode trying to format the output, telecode asks the running agent to summarize it. The agent already has full project context (recent commands, file layout, test conventions) so its 2-line summary is dramatically more useful than any heuristic we could ship. Plan §7 calls this the "killer feature" of v1.1.

The D2 decision — reuse session, share its budget

We considered three architectures before the user locked in the call:

  1. Separate Anthropic API key — cleanest cost separation, but adds a second auth surface, second rate-limit envelope, and a config step that breaks the "telegram-first, zero-setup" promise.
  2. Local rule-based summarize — no extra cost, but the whole reason rule-based is bad is exactly what we're trying to fix.
  3. Reuse the running session (chosen) — inject a hidden prompt through the same adapter that handled the user's turn. Same auth, same provider, same budget. Cost transparency comes from per-call logger.info entries so the user can audit via journalctl.

The trade-off lives in plan §10 R2 (cost transparency) and §10 R3 (context-window pollution). Mitigations: conservative threshold (default 500 chars), per-session summarize mutex (no spam under burst), and graceful fallback to the original truncated preview on timeout / error.

Design decisions

D1 — Pure helper module src/agents/summarize.ts; no adapter changes

We could have added a summarize(prompt) method to the AgentAdapter interface and asked each adapter (Claude, Codex, Cursor, Kiro) to implement it natively. We deliberately did not, for three reasons:

  • Surface stability: AgentAdapter is the v1.0 contract. Adding a method forces every existing adapter to upgrade, including the experimental Cursor / Codex adapters that aren't fully production-ready.
  • One mechanism, every adapter: routing summarize through SessionManager.dispatch reuses the same code path that handles user prompts — ANY future adapter automatically gets summarize support the day it registers.
  • Simpler reasoning: a summary call is just another agent turn. Same logging, same abort propagation, same DB updates — no parallel control flow to debug.

Signature: summarizeWithSession({ manager, store, sessionId, content, instruction, kind, timeoutMs }) returns Promise<string | null>. Callers MUST handle null by falling back to the original content — never crash, never block.

D2 — Two mutexes per session, different jobs

Three concurrency hazards lurk:

  1. User dispatch vs summarize: the user's turn holds SessionManager's per-session busy mutex; a summarize call hitting manager.dispatch mid-turn would be rejected by the isLocked short-circuit. Fix: SessionManager.waitForIdle (calls mutex.waitForUnlock). Summarize queues instead of erroring.
  2. Two summarize calls racing for the same session: e.g. user taps [💬 AI summary] on two tool_result messages within 200ms. Both would queue on the busy mutex, both would consume a roundtrip. Fix: a separate summarizeMutexes: Map<sessionId, Mutex>. runExclusive serializes them so the second call sees a fresh budget after the first returns.
  3. Two summarize calls for DIFFERENT sessions: must run concurrently (no shared state). Verified by tests/summarize.test.ts "parallel summarize calls for DIFFERENT sessions do NOT serialize" — we assert maxInflight === 2 when sidA + sidB summarize together.

The two mutexes don't compose — they protect different resources. The session-busy mutex protects the agent's wire (you can't have two adapter.run calls open with the same resume id); the summarize mutex protects telecode's cost story (you don't accidentally bill the user for redundant calls).

D3 — Threshold + env override, conservative default

500-char default (autoSummarizeThreshold()). Rationale:

  • Short outputs (single test result, one-line shell output, file-write confirmation) already fit the 240-char truncated preview cleanly. Summarizing them wastes a roundtrip and produces worse output than the raw text.
  • 500 chars is roughly 10 lines of typical bash output — well past the "I can scan this in a glance" threshold for phone-format Telegram messages.
  • Power users can tune via TELECODE_AUTO_SUMMARIZE_THRESHOLD (e.g. 0 to summarize EVERYTHING, or 5000 to only condense massive log dumps).

Verbose mode bypasses the threshold entirely — verbose users opted into the raw firehose, summarize would defeat the purpose.

D4 — Cache scope: in-memory, TTL 1h, LRU 100, session-keyed for ownership

The summary cache (SummaryCache in src/bot/summary-cache.ts) maps messageId → { fullText, toolLabel, sessionId, tsMs }. The sessionId field is critical for two reasons:

  • Ownership check: when a user taps summary:ai:<msgId> we lookup the cached sessionId, fetch the session row, and verify session.chat_id === ctx.chat.id. Mirrors the Phase C [P1] senior-review fix for diff:show — without this, user B could in theory replay user A's button.
  • Bulk eviction on session close: clearSession(sessionId) walks the cache once and drops every matching entry. The session-close paths (/session close + session:close:<id> callback) now call this alongside the existing diffCache.clearSession + toolCollapseMgr.clearSession + discardSummarizeMutex trio.

TTL 1h is intentionally long — a user might tap a button hours after the agent finished. LRU cap 100 bounds memory; opportunistic sweep on writes (no global timer pinning Node alive).

D5 — Two-phase render for auto-summarize

The dispatcher does NOT block waiting for the summary. On tool_result with preview.length > threshold:

  1. Immediate edit: replace the deferred tool_use message with 🔧 Bash · ls\n✅ Bash ok\n⏳ Summarizing 1.2KB output…. User sees feedback within the normal dispatch latency.
  2. Async summarize: void (async () => …) fires summarize, which waits for the session mutex (still held by the in-flight turn), then dispatches a hidden prompt.
  3. Second edit (success): 🔧 Bash · ls\n✅ Bash ok\n{summary} with [📜 Full output (N lines)] [💬 Re-summarize] buttons.
  4. Second edit (fail): replace placeholder with the original truncated preview body + [💬 AI summary] for manual retry. User is never stranded with a stuck "⏳ Summarizing…" message.

The placeholder body's "⏳ Summarizing N output" format encodes the size (via formatBytesShort) so the user knows whether this is a 500-byte blurb or a 12KB log.

Race-safety notes

The dispatch loop inside summarizeWithSession is structured to fail-safe:

  1. Acquire summarize mutex (queues parallel summarize calls for same session).
  2. Verify session row exists + has sdk_session_id — bail with null if not.
  3. waitForIdle against the session-busy mutex; bail with null if the overall timeout elapses during the wait.
  4. Dispatch the hidden prompt; collect text events. Stop collecting on done/error.
  5. Race the dispatch promise against a remaining-budget timeout (timeoutMs - elapsedDuringWait).
  6. Trim + return; log { sessionId, kind, elapsedMs, inputChars, outputChars } for cost auditing.

The "race the dispatch against the timeout" pattern doesn't abort the underlying dispatch — that would interrupt the user's session. It just stops waiting for the answer; the dispatch eventually finishes and its result is dropped on the floor. Acceptable: summary is best-effort, never critical-path.

Design Decisions

  • Single message per session, not per turn: the progress message exists for the lifetime of an active dispatch (start → done/error). New turn = new message; aborted turn (error) leaves a tombstone visible until next turn.
  • Throttle 1500ms: balances responsiveness (felt as "live") against Telegram limits. Throttle is a HARD GATE — dropped edits are not queued. The next event past the gate carries the latest state, which is the correct UX for a status line.
  • Idle ping ladder: 30s, 60s, 2m, 3m, 4m, 5m+. Each step reschedules on activity (reset to 30s on every update()). Past 5m+ no more pings — user should /stop themselves. Ladder is data-driven (frozen array) so future tuning is a one-line change.
  • Per-session async-mutex: start/update/finalize are serialized per session so a fast-arriving event burst cannot interleave a start mid-finalize (which would orphan a freshly-created message). Cross-session: independent mutexes — sessions for different chats don't block each other.
  • Mode awareness: verbose mode short-circuits all progress operations. The mode resolver is sync (cached) so we don't add a SQLite hit per event.
  • Sync clear(): used by session-close hooks (router.ts, commands/index.ts). It does NOT call Telegram — close paths must not block on network IO. The stale message stays on the user's screen until they scroll past, which is acceptable for an explicit close action (vs. finalize() on done/error where the daemon owns the lifecycle).
  • Bootstrap trigger: ANY event type triggers the first start() if no state exists. Originally considered "status only" but adapters vary on which event arrives first — tool_use can land before any status. Bootstrapping on first-event gives a uniform UX across Claude/Kiro/Codex/Cursor.
  • Tombstone on error, delete on done: Phase D's done-summary card supersedes the progress message; deleting avoids stale "⏳ Working…" alongside the summary. Errors leave a tombstone so a user scrolling back can correlate failures.
