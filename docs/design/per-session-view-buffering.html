Per-Session View & Stream Buffering — Design

Companion to docs/plans/per-session-view-buffering.html. Per-sub-agent sections written in parallel with code. A2 documents the Notifier refactor (silent stream sends, per-stream prefix, configurable debounce). A4 documents the notifier.* config block and the ApprovalBroker.hasPendingFor helper that gates first-come-first-active auto-switch.

A1 — OutputBuffer (per-session in-RAM ring with middle-drop)

Plan section §3.1. Foundation for B1 (SessionManager wires one buffer per session) and B2 (commands gate background events into manager.appendBuffer). Pure data structure: no I/O, no logger, only Date.now() for marker timestamps.

Context

v0.7 streams every session’s output to the chat regardless of active selection — the user sees a mix. v0.8 cuts background output off from the wire and parks it in RAM until the user explicitly switches to that session. We need a cheap, bounded buffer that:

  • Holds BufferedEvents with a stable serialization (text already formatted — the buffer just stores strings).
  • Caps at a configurable byte budget (default 50KB — ~12 Telegram messages worth) so a runaway agent can’t blow up memory.
  • Drops middle chunks when over cap (head + tail are the most informative pieces), and surfaces the loss as a visible marker line so the user understands the catch-up is partial.
  • Drains atomically: read-all-and-reset, so the consumer can’t accidentally double-flush.

Requirements (from plan §3.1)

  • OutputBuffer(capBytes = 50_000) — constructor takes optional cap.
  • append(event) — push; if total bytes > cap, drop middle, keep first 2 + last 2 + single status marker “… [N chunks omitted] …”.
  • drain() — return all events and reset internal arrays + byte counter.
  • size(), bytesUsed(), isEmpty() — observability.
  • Only trim when events.length > 4 (need room for 2 + marker + 2 = 5 final events).
  • Byte count tracked by summing event.data.length; marker is itself an event so its bytes count too.

Design decisions

  • Middle-drop, not head-drop or tail-drop. The user opening a backgrounded session cares most about (a) how it started, and (b) what it’s doing right now. The middle is the long boring tail-of-tool-calls that’s safe to summarize as a single marker.
  • Splice-in-place trim, single pass per append. events.splice(2, dropCount, marker) mutates the array once per overflow, replacing the middle slice with one marker event. dropCount = events.length - 4 so the post-splice length is exactly 5.
  • Byte recalc is incremental, not full rescan. We subtract the sum of dropped events’ data lengths and add the marker’s data length. O(dropCount) per trim — cheap even at thousands of chunks.
  • No-progress guard prevents infinite loops. Edge case: when length is already 5 and we’re still over cap (eg. last appended event itself exceeds cap, or cap is tiny relative to marker text), splice(2, 1, marker) drops one event but adds a marker that may be bigger than what was dropped — bytes go up, length stays 5, and the while condition would loop forever. After each splice we compare this.bytes against the pre-splice value; if no decrease occurred we break. The buffer is allowed to exceed cap in this pathological case; the caller (catch-up flusher) is responsible for further splitting if needed.
  • Single huge event is preserved. A 500KB tool output blob is still useful to the user; we’d rather over-shoot the cap than silently drop the last interesting event. The catch-up flusher splits Telegram messages at 3500 chars anyway, so the buffer’s job is just to keep the event reachable.
  • Date.now() for marker createdAt. Marker timestamp reflects when the trim happened, not when the dropped events arrived. This matches the marker’s semantic role: it’s a synthetic event saying “something happened around here.”
  • Marker type: 'status'. Distinguishes it from real text/tool_use so the flusher could (future) render it differently (eg. dim color, italics) without parsing the string.
  • No I/O, no logger import. Plan explicitly demands a pure data structure — lets us unit-test in microseconds, lets us reuse from any context (manager, tests, future replay tooling).

Algorithm walkthrough

// State: events = [e1, e2, e3, ..., eN], bytes > cap, N > 4
const dropCount = N - 4;                       // events to remove
const marker = { type: 'status', data: `… [${dropCount} chunks omitted] …`, createdAt: Date.now() };
const removed = events.splice(2, dropCount, marker);
// Now events = [e1, e2, marker, e(N-1), eN], length = 5
const before = bytes;
bytes = bytes - sum(removed.data.length) + marker.data.length;
if (bytes >= before) break;                    // no progress → tolerate overshoot

A2 — Notifier silent + prefix + configurable debounce

Plan section §3.3. Foundation for B2/B3: background sessions never reach the chat, active session streams must be silent (R3), and every flush needs a stable [label] prefix so users can attribute lines without re-reading the session header (R1, R4 bug fix).

Context

Pre-A2 src/bot/notifier.ts had:

  • Hard-coded const DEBOUNCE_MS = 700 — too chatty now that we want streams to be background noise.
  • Stream interface with no prefix / silent fields — callers had to manually re-prepend [label] on every chunk and could not pass disable_notification.
  • sendPlain(text, extra?) forwarded extra verbatim to grammY, with no convenience for the common “silent push” case.

v0.8 R2/R3 require: streams silent by default, debounce configurable per-instance, and a per-stream prefix set once on first append.

Requirements (from plan §3.3)

  • NotifierOpts.debounceMs?: number (default 3000) — replaces module constant.
  • Stream gains prefix: string and silent: boolean, both set on creation only.
  • appendStream(key, chunk, opts?: { prefix?, silent? }) — opts honored only on the first append for a key.
  • flush(key) composes prefix + buffer, clips to MAX_MSG_CHARS, sends/edits with disable_notification: silent.
  • sendPlain(text, { silent: true }) → disable_notification: true on the grammY call; silent key stripped before forwarding.
  • Backward compat: every existing call site (src/index.ts, src/bot/router.ts, src/bot/commands/index.ts) keeps compiling and behaving identically.

Design decisions

  • Default debounce jumps 700 → 3000ms. R2 explicitly asks for less spam. With streams now silent (R3) the cost of holding output a few seconds is zero, and Telegram’s rate budget benefits from coarser edits. Callers can still override per-instance via NotifierOpts.debounceMs — tests use 50ms.
  • Prefix set-once semantics. Subsequent appendStream(key, chunk, opts) calls ignore opts. This keeps the stream’s identity stable across the (potentially long-lived) running message and prevents callers from accidentally toggling silent mid-flight or changing prefix between edits — both would produce confusing UX. Documented in JSDoc.
  • Buffer stores raw chunks; prefix composed at flush. Two reasons: (1) idempotent — if we ever re-flush on retry the prefix isn’t doubled; (2) rotation logic operates on chunk bytes, not chunk+prefix bytes — charsSinceRotate stays meaningful.
  • silent as a convenience key, not a positional param. Keeping sendPlain’s second arg as an extra object means every existing call site ({ parse_mode, reply_markup }) keeps working. The new silent field is stripped in normalizeExtra() before forwarding so it can’t leak into the grammY payload (which would be silently ignored by Telegram, but is type-noise we don’t want).
  • disable_notification also honored verbatim. Callers that already speak Telegram’s vocabulary (eg. via spread from another extra object) get correct behavior without needing to translate.
  • normalizeExtra() returns undefined for an empty payload. Avoids sending {} upstream — harmless, but keeps tests asserting on sendMessage’s 3rd arg tidy.
  • Edit calls do not pass disable_notification. Telegram only fires push notifications on sendMessage; editing an existing message never notifies. So the silent flag is only forwarded on the (re)send paths.
  • extra as never cast preserved on sendMessage. grammY 1.43’s typed Other shape narrows by overload — passing a plain Record<string, unknown> would require declaring every conditional field. We isolate the cast to one spot (after normalizeExtra) and document the “funky” nature in the original comment.

A3 — buildSessionStrip (quick-switch inline keyboard)

Plan section §3.4. Reusable 2-row inline keyboard appended to critical messages (approval, error, done, manual-switch confirmations) so users can hop between sessions without typing /sessions. Pure builder: no I/O, no store reads — the caller passes already-fetched SessionListItem[] + activeId and gets back an InlineKeyboardButton[][] ready to spread into reply_markup.inline_keyboard or pass as extraButtons to buildSessionList / approval keyboards.

Context

v0.8 R4 (per-session view) collides head-on with v0.7’s single implicit-active session UX: the user now has to switch sessions often — once per approval, once per agent question, sometimes mid-stream to peek at progress. Forcing them to type /sessions + tap a button + return to context for every switch would burn the same patience this sprint is trying to preserve. The session strip embeds that flow directly into the messages users already pay attention to:

  • Approval prompts (loud, blocking) — the strip lets them peek at a sibling session before deciding.
  • done / error closures — the strip funnels attention into the next session worth looking at.
  • Manual /sessions list — the strip is its own row inside the list keyboard (via extraButtons), keeping the picker uniform.

The catch: Telegram inline-keyboard rows are visually narrow (~3–4 buttons fit comfortably). With more than 4 sessions we need pagination, but pagination introduces nav buttons that compete for the same row. The builder owns that layout puzzle so callers stay one-liners.

Requirements (from plan §3.4)

  • buildSessionStrip(sessions, activeId, opts?) → InlineKeyboardButton[][] (2-D rows, not an InlineKeyboard instance).
  • Default perPage = 4; default page = 1.
  • Empty list → single [➕ New session] row.
  • total ≤ perPage → row 1 = all session buttons, row 2 = single [➕ New session].
  • total > perPage → row 1 = current page slice, row 2 = [← Prev] [Next →] [➕ New] with a no-op spacer at boundaries.
  • Active session: prefix label with ● (e.g. ● refactor-auth); inactive: bare label.
  • Callback data formats (all verified < 64 UTF-8 bytes for 36-char UUIDs):
    • session button → session:switch:<uuid> (reuses B3 handler)
    • pagination → session:strip-page:<n> (1-indexed), boundary spacer → session:strip-page:noop
    • new-session → wizard:new-start (reuses existing wizard)
  • Out-of-range page clamps to [1, totalPages].

Design decisions

  • Return 2-D array, not InlineKeyboard. The strip is almost never used standalone — it’s appended to another keyboard (approval, session list, done message). Returning the raw button matrix lets callers either spread into a fresh inline_keyboard or pass as extraButtons to a sibling builder without unwrapping a grammY object. Mirrors the existing extraButtons: InlineKeyboardButton[][] contract used by buildSessionList / buildProjectList — consistent shape across the file.
  • Stable 3-button control row when paginated. The control row is always [Prev | Next | New] — at page 1 the Prev slot becomes a no-op spacer (·); at the last page the Next slot does. Visual width stays constant as the user paginates, no reflow flicker. The spacer’s callback is session:strip-page:noop so the central callback-router can swallow it with a silent answerCallbackQuery() — no error, no edit.
  • Long “➕ New session” vs. short “➕ New”. When pagination is off the single-row control gets the longer label for clarity (users not in “navigate mode”); when paginated the 3-button row uses the abbreviated ➕ New to keep the row visually compact next to ← Prev / Next →. Tiny detail, but it’s the difference between a tidy strip and a row that wraps awkwardly on narrow clients.
  • Page clamping over throw-on-stale. Pagination callbacks live forever in Telegram’s message history — a user can tap a 3-day-old session:strip-page:5 on a chat that now has only 6 sessions. Clamping (page = min(totalPages, max(1, requested))) renders something sensible instead of erroring. Cheap defensive bounds; matches the existing buildProjectList pagination contract.
  • Active marker as label prefix, not separate icon. Tried (a) a dedicated ● button alongside the active label, (b) using button callback_data distinction. (a) burns a button slot; (b) is invisible. Prefixing the label (● refactor-auth) keeps the row width at perPage buttons and gives users a glance-readable cue. The label-with-marker is still legal callback_data input upstream (the marker is on the visible text only, callback is the bare uuid).
  • Slice computed once, used twice. The function computes slice = sessions.slice(start, end) once and maps it to button objects. Avoids accidental off-by-one between active-detection and label rendering. Cheap (perPage ≤ 8 typical).
  • No label truncation. Plan §3.4 doesn’t cap label length; v0.7’s label regex already restricts to 1–32 chars, well within Telegram’s inline-button text limit (64 chars). Adding ellipsis logic here would be premature.
  • Callback-byte audit baked into the test suite. Spec #11 generates 36-char UUIDs across 3 pages and asserts Buffer.byteLength(callback_data, 'utf8') < 64 on every button. Prevents a future label/format change from silently exceeding Telegram’s limit (which would manifest as the button being dropped from the message, not as an error).

A4 — Config schema + ApprovalBroker.hasPendingFor

Plan sections §3.3, §3.5 and the file-changes table (src/config.ts, src/approval/broker.ts). This sub-agent ships the two low-risk plumbing pieces that B1/B3 will lean on: a notifier block in the config schema (so debounce + buffer cap become user-tunable instead of magic constants), and a one-liner helper on ApprovalBroker that lets the router answer the question “does any other session in this chat already own a pending approval?” without exposing the broker’s internal map.

Context

Three needs surfaced as B-phase sub-agents started wiring per-session gating:

  • Notifier debounce is hard-coded. A2 introduced an opts.debounce override, but there’s no path from ~/.telecode/config.yaml to the default. Users wanting a slower / faster “live feel” had to patch source.
  • OutputBuffer cap is hard-coded. A1 defaults capBytes = 50_000. Same problem — the operator can’t tune catch-up depth.
  • Auto-switch race. Plan §3.5 specifies that when a background session raises an approval, the router auto-switches that session to active only if no other session has already grabbed focus via its own pending approval. Without a peek API on the broker, B3 would have to either keep its own shadow map (drift-prone) or scan via the existing pendingForSession per-session (O(N) loops). A single chat-scoped predicate is cleaner.

Requirements (from plan)

  • notifier.debounce_ms: positive int, default 3000.
  • notifier.buffer_cap_bytes: positive int, default 50_000.
  • Both fields optional (existing configs must keep validating — safe defaults via z.default).
  • config.example.yaml shows both keys with explanatory comments (debounce ↔ notification spam, buffer cap ↔ catch-up depth).
  • ApprovalBroker.hasPendingFor(chatId, excludeSessionId?): returns true iff some pending request matches chatId and is not owned by excludeSessionId. Used by router auto-switch gate.
  • Tests: empty broker → false; two sessions same chat → hasPendingFor(chat, A) sees B; resolving B drains the predicate for A; cross-chat requests don’t leak.

Design decisions

  • Block-scoped schema, not flat keys. Following the existing pattern (agents.claude, daemon.workspace_scan), the new fields land under notifier: so future per-notifier knobs (eg. max_msg_chars, rotate_on) cluster cleanly. Avoids polluting the top-level namespace.
  • Explicit object default, not .default({}). Zod v4 rejects partial defaults on objects whose inner fields each have their own .default() — the outer default must satisfy the full output shape, not the input shape. Matches what daemon.workspace_scan already does in the same file.
  • Wide range, no upper cap. debounce_ms is z.number().int().positive() — no max. A user wanting a 30s debounce for a quiet long-running session is valid; clamping would surprise. Same for buffer_cap_bytes.
  • hasPendingFor early-exits on first match. Loop over pending.values() — return true as soon as a matching request is found, instead of building an intermediate array (cf. pendingForSession which materializes). Cheaper for the common case where N pending is tiny but called on the hot path of every approval prompt.
  • excludeSessionId is optional. Default undefined ⇒ “is anything at all pending in this chat?”. Router uses the typed form; future callers (eg. health endpoint) can use the simpler form.
  • No new public type surface. Signature is (chatId: number, excludeSessionId?: string) => boolean. No new exported interfaces, no rename of existing methods — pure addition.

Pending-state shape (for downstream B3)

Internal pending map is Map<string, { request: ApprovalRequest; resolve; timer }>. ApprovalRequest carries both chatId and sessionId, so the predicate filters in a single pass without touching the per-session index.

hasPendingFor(chatId: number, excludeSessionId?: string): boolean {
  for (const p of this.pending.values()) {
    if (p.request.chatId !== chatId) continue;
    if (excludeSessionId && p.request.sessionId === excludeSessionId) continue;
    return true;
  }
  return false;
}

}

B1 — SessionManager wires OutputBuffer

Owner: B1 sub-agent · depends on A1 (OutputBuffer) and A4 (config + broker). Adds per-session output buffers to SessionManager so B2 can route background events into them and B3 can drain them on switch / approval auto-switch.

Requirements (from plan §3.2)

  • Add Map<sessionId, OutputBuffer> to SessionManager.
  • Expose appendBuffer(sessionId, event), drainBuffer(sessionId), hasBuffered(sessionId).
  • Constructor accepts bufferCapBytes from config.notifier.buffer_cap_bytes (default 50_000).
  • Backward compatible — existing new SessionManager(store, registry) call sites (5 of them across src/index.ts + 4 test files) must keep compiling.

Design decisions

  • Options object as third positional arg, not constructor overload. The existing signature is (store, registry) — positional. Rather than reshape the whole API to (store, registry, { ... }) required, we add an optional third arg opts: SessionManagerOpts = {}. This keeps every existing call site (5 of them, including 4 in tests) source-compatible without edits. Future knobs land in the same opts bag, no further breaking changes.
  • Buffers map keyed by sessionId, lazy-created. Sessions that never go to background never allocate an OutputBuffer. The map entry is created on first appendBuffer — cheap, predictable, GC-friendly.
  • Cap captured into readonly bufferCapBytes field in the constructor so all lazy-created buffers honor the same per-manager config. We do NOT re-read config inside appendBuffer — cap changes require daemon restart, matching how the rest of loadConfig() is consumed in src/index.ts.
  • Buffer Map entry left in place after drain(). The OutputBuffer instance is cleared but kept — future appends in the same session reuse it without allocating a new buffer. Memory cost is one empty OutputBuffer per session that ever buffered, which is trivial.
  • No session-close cleanup yet. SessionManager has no close() path today — store.close() happens at daemon shutdown; interrupt() just aborts the in-flight dispatch but the session stays live. Buffer drain on close belongs to a future sprint (or B3 when the switch handler exists). Plan §7 Risk register P2 acknowledges this.
  • hasBuffered returns false for unknown sessions — matches drainBuffer returning []. Callers (B3 switch handler) can treat “no buffer” identically to “empty buffer” without a special case.
  • BufferedEvent re-imported from ./output-buffer.js so callers can type their own event factories without reaching past SessionManager.

Design decisions

  • Helper placement: flushBufferedAsCatchUp lives as a top-level exported function in the same file rather than a new module. The helper is small (5 lines) and only consumed by B2 + the test suite; a dedicated buffer-flush.ts file would have been over-modularization. Exporting it keeps the test deterministic without monkey-patching the inline closure.
  • Re-read activeId per event: the dispatch's cur is captured at start-time. The active session can flip mid-dispatch (user taps a switch button while agent streams). Every onEvent invocation calls store.getChatState(chatId).active_session_id fresh — never cached outside the callback. The test mid-dispatch active flip asserts that the same dispatch streams while active then buffers after the switch.
  • Async ordering in done/error: both branches wrap their work in an immediate async IIFE wrapped in void, so the synchronous adapter callback returns immediately but the catch-up → closeStream → final message chain awaits in order. Catch-up first (silent), closeStream second (flushes any pending streamed text), then the done/error message last (NOT silent — user gets the push notification). The previous v0.7 code used a .then() chain that didn't guarantee catch-up happened before the close.
  • Catch-up is silent: flushBufferedAsCatchUp sends { silent: true } because the immediately-following critical message provides the push. Stacking two notifications for one logical event would spam.
  • Label prefix: every active-session send prepends [label] (with trailing space). For streamed text this is set once on first appendStream call via the prefix option (A2 set-once semantics); for tool_use/critical it's prepended manually. Background events stored in the buffer do not include the prefix — the catch-up header already names the session, and adding the prefix per event would double-label after the header.

Edge cases observed

  • Buffer empty at done/error: flushBufferedAsCatchUp is a no-op when drainBuffer returns [] — satisfies plan acceptance criterion “Switch session khi buffer empty → không spam empty catch-up message”. Tested.
  • Active flip mid-dispatch: the closure does not cache active state. A switch from A→B mid-stream causes subsequent events to buffer rather than stream. The user sees a clean cut-off at the switch moment, with the rest in catch-up on next switch back or at done.
  • Session closed mid-dispatch (e.g. /session close A while A is running): setActiveSession(chatId, null) is called inside /session close. Subsequent events for A see activeId === null, so isActive evaluates false → events go to buffer. The buffer is drained on the closing done as a silent catch-up + the [A] ✅ done message still notifies. Not a leak, but the closing message arrives in the chat even after the user explicitly closed — acceptable (the user asked to interrupt, the final state still has value). No active session is required to receive the message; notifier targets the chat directly.
  • Race — tool_use is fire-and-forget: the active-branch sendPlain for tool_use uses void notifier.sendPlain(…) so order between text-stream flushes and tool_use markers depends on debounce timing. Pre-existing v0.7 behavior; B2 preserves it (test asserts sendPlain is called but does not assert interleaving with appendStream).

Design decisions

1. Extract createApprovalPrompter factory. The previous broker prompter was an inline object literal inside startBot. Testing auto-switch that way would have needed a full Bot + sqlite + manager + broker scaffold per case. We extracted into a pure factory with narrow Pick<…> deps so tests pass real ApprovalBroker + SessionStore + SessionManager instances and only mock the notifier. The factory returns the same { prompt, notifyTimeout } shape; behavior is byte-for-byte identical to the inline version, the refactor is purely test-seam.

2. Combine approval buttons + session strip via approvalKeyboard extension. Two alternatives:

  • Manual InlineKeyboard composition at the call site — merge approvalKeyboard(id).inline_keyboard with buildSessionStrip(…). Works, but spreads row-building across files and duplicates the merge pattern at every new caller.
  • Add an extraButtons param to approvalKeyboard — mirrors the existing pattern in buildSessionList / buildProjectList (both already accept extraButtons: InlineKeyboardButton[][]).

Chose the second. approvalKeyboard(requestId, extraButtons = []) appends each inner array as a row after the existing decision rows; empty inner arrays are skipped defensively. The 1-arg call path is preserved — no other call sites needed updating.

3. Silent semantics on auxiliary messages. The switch notice (🔔 Đã chuyển sang ...) and the catch-up dump ([label] 📥 catch-up ...) are both sent with { silent: true }. The approval prompt itself is the “loud” notification — doubling up would spam. The Notifier maps silent: true to Telegram disable_notification: true (A2 semantics).

4. Catch-up header consistency. The router’s catch-up emits [label] 📥 catch-up (N events from background): — the exact wording used by flushBufferedAsCatchUp in commands/index.ts (B2). Users see the same header regardless of trigger: auto-switch on approval, manual switch on tap, done/error flush from the dispatch loop. We didn’t import the helper because the prompter uses a structural mock-friendly ApprovalPrompterNotifier interface while the B2 helper requires the concrete Notifier class. Wording is duplicated literally in 3 places — small price for narrow test seams.

5. Wizard guard (plan §7 P2) — accepted limitation. The broker callback runs outside any ctx, so we can’t inspect ctx.conversation.active() to defer the auto-switch while the /new wizard is mid-step. Options considered: (a) plumb conversations state through SessionStore (over-engineering — the storage adapter is in sqlite but reading "is wizard X active" from outside the plugin is fragile); (b) skip switch entirely when any wizard might be active (false negatives in the common case — user is not in a wizard); (c) accept the limitation. We chose (c): the /new wizard is short-lived (3 steps, ~30s), the user can /cancel, and both auxiliary messages are silent so they don’t yank focus visually. The approval prompt itself does notify — correct, the agent is genuinely blocked. Documented in the prompter’s JSDoc.

6. Question events. Plan mentions question events but src/agents/types.ts AgentEvent currently has no question variant. Agent questions reach the user through the existing approval mechanism today (a tool that needs approval → user answers via Allow/Deny). If a dedicated question event lands later, mirroring this flow is a 5-line copy of the auto-switch block in createApprovalPrompter.prompt. No code change needed for B3.

7. Manual switch flush. switchSessionHandler already called setActiveSession and emitted the transcript-tail preview. We append a buffer check + silent catch-up reply after the existing reply — wrapped in try/catch so a transient Telegram error on catch-up doesn’t mask the successful switch (the user has already seen the 📍 [label] preview).

Patches applied during review loop

[P1] splitCatchUp for Telegram’s 4096-char limit. The catch-up flusher in B2/B3 joined all buffered events into one string and handed it to notifier.sendPlain. With the OutputBuffer cap at 50KB and a runaway agent producing many medium-sized chunks, the joined payload routinely exceeded Telegram’s per-message 4096-char hard cap — the message would be silently clipped server-side and the user would lose the tail of the catch-up. Fix: added splitCatchUp(header, contHeader, lines, maxChars = 3400) in src/bot/reply-builders.ts that splits at line boundaries (keeping events together), falls back to hard char cuts when a single line exceeds the cap, prepends the full header on part 1 only and a short [label] 📥 catch-up (cont.): header on subsequent parts. 3400 sits comfortably under both the notifier’s MAX_MSG_CHARS (3500) and Telegram’s 4096 so neither layer needs to re-clip. Wired through flushBufferedAsCatchUp (commands) and the router’s auto-switch path. Added 6 specs covering empty input, single-part, exact-cap boundary, multi-part split at line boundary, oversize-single-line hard split, and pathological tiny maxChars.

[P2] Buffer leak on /session close. Closing a session via /session close <label> called store.setActiveSession(chatId, null) and aborted the in-flight dispatch, but the per-session OutputBuffer entry in SessionManager.buffers stayed in the Map forever. Across a long-lived daemon (the v0.8 target install profile is launchd, days/weeks uptime), repeatedly creating + closing sessions would accumulate buffer entries even after the session row was deleted — each buffer holds up to bufferCapBytes bytes of dangling chunks. Not a P0 (single buffer is ≤ 50KB, hundreds of closed sessions ~MB scale), but it’s an unbounded growth path on a long-running daemon. Fix: added SessionManager.discardBuffer(sessionId) that this.buffers.delete(sessionId) — idempotent on unknown ids. Called from the /session close handler immediately after the close confirmation. Added 1 spec asserting hasBuffered flips to false after discard and a subsequent appendBuffer lazily allocates a fresh buffer (no stale state).
