P0.1 — 🔀 Switch khác wired to /sessions

Context

The wizard success message used to attach two inline buttons whose callbacks were ack-only stubs (session:list-trigger, session:logs-trigger). Tapping either showed a toast hint “Dùng /sessions” — functional but dead-click UX.

Decision

  • Reuse the existing buildSessionList reply-builder (returns the same payload /sessions uses) instead of writing a parallel renderer. Single source of truth for session-list shape.
  • Reply with a NEW message rather than editMessageText on the wizard success bubble — editing would destroy the “session created OK” record the user needs as a permanent audit trail.
  • The callback carries no payload (chat id is available from ctx.chat.id); listing is chat-scoped by definition.

P0.2 — 📋 Tail logs wired to /status logs 30

Context

The original button had no sessionId in its callback data — the router couldn’t know which session’s logs to render. Without a payload, the handler had to fall back to the active session, which is wrong when the user switches away from the freshly-created session before tapping “Tail logs”.

Decision

  • Embed sessionId in the callback data: session:logs-trigger:<id>. Verified callback_data length is well under Telegram’s 64-byte cap (session:logs-trigger: = 21 chars + 36-char UUID = 57 bytes).
  • Update successKeyboard() in src/bot/wizards/new-session.ts to accept a sessionId parameter; the wizard’s final ctx.reply passes the just-created session’s id.
  • Handler validates the session exists + belongs to the chat (defensive against stale callbacks after a session-close), then renders the same fenced-code-block format as /status logs with up to 30 rows.

File Changes

  • src/bot/wizards/new-session.ts — successKeyboard() now takes sessionId: string. Callsite updated to pass created.id.
  • src/bot/router.ts — t3SessionLogsTrigger closures now reads payload as the session id, validates via store.getSession + chat_id check, and tails store.tailToolLog(sessionId, 30).

P0.3 — Follow-up inline suggestions

Context

Plan Tier-3 #7: after a tool finishes, append 2–3 inline buttons that hint at common follow-up actions so the user can drive the agent without typing. The extraButtons hook on reply-builders.ts existed but had no consumer.

Decision

  • Heuristic, no extra LLM call — map (toolName, exitCode) to a fixed set of buttons:
    • fs_write success → [📄 Xem file] [▶️ Tiếp tục] [↩️ Rollback]
    • execute_bash / Bash / shell → [▶️ Tiếp tục] [🔁 Run again]
    • default → [▶️ Tiếp tục]
  • Callbacks just acknowledge with a Vietnamese hint (e.g. “Gõ tiếp tục hoặc prompt mới để agent đi tiếp.”). Doesn’t auto-dispatch — keeps the user in control.
  • Hard 64-byte budget per callback_data with a defensive guard: if a view-file button’s data would overflow (very long path), the button is silently dropped rather than crash the message.
  • Wired into the live tool_use event branch in src/bot/commands/index.ts — only for ACTIVE sessions, since background sessions buffer plain text (suggestions belong to the foreground flush).

  • src/bot/commands/index.ts — tool_use branch now builds a 1-row InlineKeyboard from buildSuggestions and passes it as reply_markup alongside the existing silent: true. Added extractFilePath helper (exported for tests).
  • src/bot/router.ts — 5 new callbackRouter.on('suggest', '', ...) registrations.

P0.4 — 📌 Forever persistent allow

Context

Plan decision D4: 🌟 Allow always is session-scoped (lost on daemon restart); users need a way to whitelist a tool+input pair into policy.yaml for permanent allow. Tier-3 #8.

Decision — 2-step confirm UX

  1. The approval prompt now carries 4 buttons (2 rows): [✅ Allow once] [🌟 Allow always] / [📌 Forever] [🚫 Deny].
  2. Tap [📌 Forever] → editMessageText pivots the SAME message into a confirm body (“⚠️ Ghi vĩnh viễn quyền: <tool> với args <...>?”) and swaps the keyboard to [✅ Xác nhận] [❌ Hủy].
  3. Tap ✅ Xác nhận → PolicyEngine.appendRule(toolName, input, 'allow_always') writes policy.yaml atomically (tmpfile + rename, inherits from appendList); broker resolves the approval as allow_always; user gets a confirmation reply pointing at ~/.telecode/policy.yaml for hand-edits.
  4. Tap ❌ Hủy → editMessageText restores the original 4-button approval keyboard. No policy write, no broker resolution.

Pattern derivation

PolicyEngine.buildPattern(toolName, input) renders the input via the same renderInputForMatch pipeline used at decision time, then escapes glob meta (*, ?) so the persisted rule is an exact literal match — users get what they tap, not a wildcard.

  • { command: 'npm run lint' } → Bash(npm run lint)
  • { command: 'echo *' } → Bash(echo \*)
  • No-arg inputs ({}, '', null) → bare tool name (Read)

P0.5 — /dashboard live status loop

Context

Plan Tier-3 #9: a single editable Telegram message refreshed every 2s with a live snapshot of daemon state (sessions, pending approvals, active wizards, buffer sizes).

Decision

  • Pure rendering — renderDashboard(snapshot) is a pure function so tests can exercise every rendering branch deterministically.
  • Loop runtime — DashboardLoop owns the interval timer + idle clock; it consumes a DashboardEditor interface (sendInitial / editMessage) so the production wiring in commands/index.ts can adapt grammY’s API while tests inject a fake editor.
  • Stop conditions — manual (/dashboard stop), message-deleted (decoded from Telegram’s “message to edit not found” 400), 5-minute idle (now - lastActivityAt ≥ idleTimeoutMs), with a per-chat singleton map so re-running /dashboard while one is live shows a hint instead of starting two loops.
  • Rate-limit safety — on a 429 / “Too Many Requests” the editor returns reason: 'throttled' and the tick is silently skipped (no stop). On “message is not modified” we treat as success (no-op render).
  • User-activity hook — the plain-text message handler calls dashLoop.markUserActivity() so an active chat resets the idle clock without piping every event through.
  • Refresh rate — 2s fixed per plan decision D6; not user-tunable.

P0.6 — Wizard-aware auto-switch

Context

The approval prompter (factored out of startBot as createApprovalPrompter) runs OUTSIDE any grammY context — it’s invoked by ApprovalBroker.ask on the broker’s internal call stack. That means it can’t read ctx.conversation.active(). Result: if an approval lands while the /new wizard is mid-step (label input), the auto-switch flips active focus and hijacks the wizard’s text input.

Decision

  • Shared singleton — new wizardState object in src/bot/wizard-state.ts tracks Set<chatId> of active wizards + a Map<chatId, queue> of deferred callbacks. API: enterWizard(chatId), exitWizard(chatId), isWizardActive(chatId), deferUntilWizardExits(chatId, fn).
  • Plugin hook — conversations({ onEnter, onExit }) mirrors entry/exit into the singleton. Verified via Context7 (/grammyjs/conversations) that these hooks are passed at plugin init (not per-conversation).
  • Prompter integration — createApprovalPrompter now takes an optional wizardGuard dep (defaulting to the singleton). Before auto-switching, it checks guard.isActive(chatId); if active, it enqueues the switch via guard.deferUntilWizardExits instead of running it inline.
  • Manual-switch race — we snapshot the active session id at the moment of deferral (activeAtDeferral). When the queued switch fires, it compares against the current active id: if the user manually flipped sessions while the wizard was open, we abort and respect their choice.
  • FIFO ordering — multiple deferred switches for the same chat fire in arrival order on exitWizard. Errors in any single handler are swallowed (logged) so one bad callback doesn’t strand the rest.

File Changes

  • NEW src/bot/wizard-state.ts — singleton + functional helpers.
  • src/bot/router.ts — conversations({ onEnter, onExit }) wiring; ApprovalPrompterDeps.wizardGuard optional dep; runAutoSwitch takes expectedActive for manual-switch detection.

Verification

  • tests/wizard-state.test.ts — 6 tests: enter/exit toggling, immediate-fire when no wizard, queue + FIFO, error isolation, per-chat isolation.
  • tests/auto-switch.test.ts — 3 new tests in “P0.6 wizard-aware auto-switch”: defers while active, no defer when inactive, deferred re-check respects user manual switch.

P1.1 — Adapter registry open-set

Context

Pre-P1 closed-set: adding an adapter required edits to 7+ files (types literal union, registry constructor, config schema union, wizard hardcoded picker, reply-builders hardcoded badge map, dashboard hardcoded ternary, commands /session new validation). This made P3 (Codex) and P4 (Cursor) impossible to land cleanly — they would each carry a 4-file diff just for plumbing. P1.1 rewrites the seam so adding an adapter is one file (the adapter) plus one line in src/agents/index.ts.

Decision

  • AgentKind is now string. Runtime validation lives in the registry (require() throws with the known-kinds list) and the config loader (knownKinds cross-check).
  • AgentRegistry is a plugin container with register(kind, factory, metadata), get(kind) → AgentAdapter | undefined, require(kind) (throwing variant), has(kind), kinds() (sorted), and list() (sorted metadata for UI).
  • Factories are lazy + memoized so registering a heavy adapter (Claude SDK) doesn’t pay the construction cost until the first session of that kind runs.
  • src/agents/index.ts is the single registration point. Built-in adapters wire through registerBuiltinAdapters(registry, deps): missing deps.claude means the registry skips claude (useful for tests + future "Cursor-only" deployments).
  • Each adapter exports an AdapterMetadata const (kind, displayName, badge, description?). The wizard picker, dashboard, and reply-builders read from registry.list() — no inline badge tables left.
  • Config agents is now z.record(z.string(), base.passthrough()). Built-in overlays (claude / kiro) are applied in a post-parse pass so existing typed access (config.agents.claude .setting_sources) keeps working. Unknown keys pass through verbatim so a future codex:/cursor: section needs no schema change.
  • Cross-check is OPTIONAL on loadConfig(path, knownKinds?): callers that know the registry pass it in and get friendly "unknown agent kinds: codex" errors at boot time; bare callers (tests, scripts) skip cross-check.

P1.3 — /screenshot platform gate

Context

v0.8 /screenshot shelled out to screencapture unconditionally. Linux daemons returned screenshot error: ENOENT and Windows users got the same. P1.3 adds platform-specific capture so the same Telegram command works on all 3 OSes that Telecode targets after P5.

Decision

  • Factored capture into a pure captureScreen(outPath, exec?, platform?) helper. Production callers omit exec/platform; tests inject fakes to exercise all 3 branches from a single macOS host.
  • darwin — preserved screencapture -x; the macOS-specific Screen Recording permission hint stays since it’s the most frequent real-world failure mode.
  • linux — probe priority order grim → gnome-screenshot → scrot via tool --version (universally supported, fast). First tool whose probe returns exit 0 is used. If the chosen tool then fails the capture, we surface the exit code (rather than fall through silently) so a Wayland permission issue or DISPLAY-missing scrot doesn’t hide behind a "no tools found" message. No tools at all → helpful apt install hint.
  • win32 — PowerShell snippet using System.Windows.Forms.Screen::PrimaryScreen.Bounds + System.Drawing.Bitmap + Graphics.CopyFromScreen; saved as PNG via Bitmap.Save(path, [System.Drawing.Imaging.ImageFormat]::Png). Single quotes in the output path are escaped (doubled) per the PowerShell literal-string rule so paths containing apostrophes work.
  • Output path always path.join(os.tmpdir(), 'telecode-screen-${ts}.png').

File Changes

P2.1 — install-systemd.sh + uninstall-systemd.sh

Context

Pre-P2 Telecode only shipped install-launchd.sh (macOS). Linux users had to manually figure out a systemd unit, the file location, permissions on ~/.telecode, the node binary path under NVM, PATH composition for the unit, and how to enable it as a user service. This is the same friction the launchd installer eliminates for macOS. P2.1 mirrors that ergonomic on Linux.

Decision — structural mirror of install-launchd.sh

  • Same shape: bash with set -euo pipefail, same bold/ok/warn/err helpers, same numbered-step output ordering. A reader who knows the launchd installer can read the systemd one without surprises.
  • Atomic writes: atomic_write helper does mktemp + mv -f for every generated file (config.yaml, .env, unit file). Avoids the “crash during write leaves corrupt half-file” class of bug. trap cleanup EXIT removes any stray tmpfile if the script aborts; the trap returns 0 explicitly to avoid masking the script’s real exit code (a subtle set -e + EXIT-trap interaction that bit our first test run).
  • Permissions: install -d -m 0700 on ~/.telecode + ~/.telecode/logs; chmod 0600 on config.yaml and .env; unit file is 0644 (must be readable by systemd’s user manager).
  • Node detection: command -v node first, NVM fallback (highest installed version under ~/.nvm/versions/node). Whatever path we resolve goes verbatim into the unit’s ExecStart= as an absolute path — systemd has no shell, so PATH lookups would fail.
  • Install-dir detection: if the script was launched from a checkout that has dist/index.js, use that. If a checkout without a build, still use it (we’ll npm run build later in the same script). Fallback /opt/telecode. Override via TELECODE_INSTALL_DIR env.
  • Prompts vs env: prompt_or_env helper reads the env var if set (including set-to-empty for optional fields, distinguished via ${!name+x}), else prompts on a tty, else fails for required fields. Supports CI / Ansible / cloud-init use cases where there’s no tty.
  • PATH composition: the unit’s PATH starts with the node binary’s directory (so npm/npx resolve when the daemon shells out), then the standard system paths. De-duped via awk in case node lives under /usr/local/bin.
  • --dry-run: every side-effecting call goes through run_cmd; in dry-run we printf '+ %s\n' instead of executing. atomic_write is bypassed too — the rendered body prints to stdout, indented 4 spaces. This is what the integration test parses.
  • Lingering hint: after install, check loginctl show-user $USER | grep Linger and print the sudo loginctl enable-linger hint if the user hasn’t enabled it. Crucial for headless servers (default systemd --user instance dies on logout).
  • Uninstall: systemctl --user disable --now, rm -f unit file, daemon-reload, then prompt (or honor --purge / --keep-data flags) about deleting ~/.telecode. Default = keep (so reinstall is seamless).

P3.1 — CodexAdapter interface + config overlay

Context

Codex CLI’s codex app-server is a JSON-RPC daemon mode designed exactly for embeddings like ours: persistent stdio channel, threads to scope conversations, turns to scope individual user prompts, and a built-in permission-request protocol that maps cleanly onto Telecode’s existing ApprovalBroker. No HTTP, no auth juggling, no hook bridge (contrast Kiro which needs a loopback HTTP receiver). The adapter is pure protocol glue.

Decision — transport seam for testability

  • Plug-in transport. The adapter is parameterised on a CodexTransportFactory interface; the default factory spawns execa('codex', ['app-server'], { stdio: 'pipe' }) and wires stdout to readline.createInterface. Tests inject a FakeTransport that captures outbound JSON-RPC and lets the test drive inbound notifications. No real binary is ever spawned in CI.
  • Sequential message queue. Codex streams a high frequency of notifications (text deltas + exec output deltas). If we handled each inbound message in its own microtask, an await broker.ask on a permission request could interleave with text deltas that arrive while the user is reading the Telegram approval prompt — resulting in out-of-order rendering. The MessageQueue wraps the per-message handler in a serial drain so each notification fully resolves before the next starts. Unit tested independently.
  • Pending request map. Outbound requests carry a monotonic numeric id; inbound responses look up the id in a Map<number, resolver>. JSON-RPC error responses reject the promise with the upstream message verbatim so the surrounding try/catch can map auth-flavoured errors to the friendly hint.
  • Non-experimental capabilities. We deliberately do NOT set capabilities.experimentalApi: true in initialize — experimental fields are gated server-side and the rejection error (<descriptor> requires experimentalApi capability) would bubble back to the user as a confusing fault. Sticking to the stable surface keeps the adapter forward-compatible across Codex versions.

Config schema

const codexOverlay = z.object({
  command: z.string().default('codex'),
  model: z.string().default('gpt-5.1-codex'),
  effort: z.enum(['low', 'medium', 'high']).default('medium'),
});

No binary field (Codex uses command per the Codex 0.75 docs); no networkAccess field (hardcoded to true per plan decision D5 — users who want air-gapped sandboxing can fork the adapter later, but exposing it as config would invite policy mismatches with ApprovalBroker); no sandboxPolicy.type override (always workspaceWrite with writableRoots = [session.cwd] — matches Codex’s per-thread sandbox best practice).

P3.2 — Lifecycle & event mapping

Protocol sequence

1. spawn `codex app-server`
2. send  `initialize`        { clientInfo, capabilities: {} }
3. recv  result               { capabilities }
4. send  `initialized`        notification
5. send  `thread/start`      { cwd }
6. recv  result               { threadId }      (may also arrive via `thread/started` notif)
7. send  `turn/start`        { threadId, input: [{type:'text', text: prompt}],
                               cwd, approvalPolicy: 'unlessTrusted',
                               sandboxPolicy: { type: 'workspaceWrite',
                                                writableRoots: [cwd],
                                                networkAccess: true },
                               model, effort }
8. recv  notifications:
     - `turn/started`               → emit status
     - `item/started`               → emit tool_use (commandExecution/toolCall)
     - `item/agentMessage/delta`    → emit text
     - `item/updated`               → emit text (fallback for older builds)
     - `item/completed`             → emit tool_result OR final text
     - `command/exec/outputDelta`   → base64 decode → emit text
     - `item/permissions/requestApproval` (request) → broker.ask → respond
     - `turn/completed`             → emit done, resolve runPromise
9. close stdin → wait child exit (5s timeout) → SIGKILL on timeout

Event mapping rationale

  • item/started{type: 'commandExecution'} → tool_use with tool: 'codex.exec', input = the command array. Distinct from toolCall (dynamic tool) which emits tool: it.tool ?? it.name ?? 'codex.tool' — user sees the actual tool name in their Telegram tool log.
  • item/completed with the same item types emits a tool_result with ok: it.success !== false; final agent message text is emitted only when the item has a top-level text field (Codex builds split: some stream via delta, others only emit text at item/completed on the final assistant turn).
  • command/exec/outputDelta.deltaBase64 is decoded with Buffer.from(s, 'base64').toString('utf8'). Decode errors are silently swallowed — a partial multibyte UTF-8 sequence on the chunk boundary would not show up as a problem in practice (the next chunk completes it) and emitting a partial-decoded fragment is better than dropping it.
  • turn/completed.turn.error, when present, emits an error event before the done; matches Claude adapter behaviour for turn-level failures.

Approval routing

Server emits item/permissions/requestApproval as a JSON-RPC REQUEST (has id + method + params). The adapter MUST send a response with the same id. Mapping:

Broker decisionJSON-RPC response
allow_once{ scope: 'turn', permissions: <requested> }
allow_always{ scope: 'session', permissions: <requested> }
deny / timeout{ permissions: {} } — per Codex docs “omitted permissions are treated as denied”.

The broker prompt sees toolName: 'codex.permissions' with the full Codex params object as input (preview is the JSON-stringified params, truncated to 240 chars). Reuses existing approval UI — no Codex-specific Telegram widget needed.

Abort + shutdown

  • Abort: AbortSignal from SessionManager.interrupt → send turn/cancel { threadId, turnId } as a notification (best effort, ignored if Codex doesn’t support it) → close transport with 2s grace period.
  • Graceful close: in the finally block we call transport.close(5_000) — the default transport closes stdin (letting the server flush) and waits up to 5s for the child to exit, then SIGKILLs. Verified by the “force-kills transport when child does not exit within close timeout” test.
  • Aborted × non-zero exit: if we aborted on user request, we suppress the “exited with code N” error event (the abort itself is the user-visible signal). Otherwise the exit code + stderr tail are surfaced as error, with the auth-error regex intercepting first.

P3.3 — Native auth (D1)

Decision

Per plan decision D1: Telecode never handles Codex auth. The adapter does not read OPENAI_API_KEY, never invokes codex login, never opens a browser. The user is expected to have codex login completed in their shell environment before the daemon starts (or to have set OPENAI_API_KEY in the systemd/launchd unit’s Environment). If Codex CLI surfaces an unauthenticated error at any point, we map it to a clear Vietnamese hint:

"Codex CLI chưa login. Chạy 'codex login' (hoặc set env var)
trước khi dùng adapter này. Chi tiết: <upstream error>"

Detection happens in three places:

  1. Real-time stderr scan (regex AUTH_ERR_RE — unauthenticated / not authenticat / please run codex login / no API key).
  2. Stderr tail when the child exits with a non-zero code.
  3. The catch arm around the JSON-RPC request promises — if Codex returns an error response containing one of those phrases, we map to the same hint instead of the raw message.

The authErrorSurfaced latch ensures we emit the hint at most once per session even if all three detection paths fire.

Phase 4 — Cursor CLI adapter

Context

Cursor CLI ships a first-class integration mode — cursor-agent acp — that implements the Agent Client Protocol (ACP) over stdio. ACP is a JSON-RPC 2.0 protocol designed by Zed / Cursor with the explicit goal of letting any client embed any agent: there’s no Cursor-specific wire format the way Codex 0.75 has its own thread/turn/item schema. Methods are namespaced (session/new, session/prompt, session/request_permission, session/update), and the permission response uses a generic “outcome envelope” ({ outcome: { outcome: 'selected', optionId: '…' } }) rather than Codex’s “scope + permissions echo” pattern.

The plan calls Cursor a 2 day phase because the wire format is protocol-standardised — the adapter ends up smaller than Codex (no per-version method renames, no base64-encoded exec stream, no thread-vs-turn separation). The trade-off: we cannot reuse the Codex adapter directly because every method name, payload shape, and the permission outcome envelope differs. We keep one adapter per protocol so upstream contract changes localise to one file.

Design decisions

  • D1 (re-affirmed) — Auth = native. Telecode never runs authenticate in the ACP handshake. The user is expected to cursor-agent login once on the host; Cursor persists the token (~/.cursor/auth.json or platform keychain). At initialize time we declare client capabilities and proceed straight to session/new. If session/new fails with an auth error we surface the Vietnamese hint “Cursor CLI chưa login. Chạy 'cursor-agent login' trước khi dùng adapter này.”
  • Binary name — cursor-agent (not agent). Cursor’s docs alternate between agent (in code snippets) and cursor-agent (in install instructions). Both Homebrew (brew install cursor-cli) and the curl installer drop a cursor-agent symlink. We default to the disambiguated name to avoid PATH collisions with other tools named agent. Users with a different binary name override via agents.cursor.command.
  • Default model = auto. Cursor adds / retires models out-of-band; pinning a specific id (e.g. gpt-5.2) would force a config change every time. The server interprets auto as “pick the latest you have”. Users who need determinism can pin via agents.cursor.model.
  • Permission option ids — kebab-case. ACP convention is allow-once, allow-always, deny — matching the Cursor UI’s own ids so the server’s allow-always cache stays coherent. The mapping is centralised in decisionToOptionId() and unit-tested.
  • MessageQueue duplication (vs DRY) — intentional. The Codex adapter has an identical sequential drain queue. Lifting it into a shared helper would require widening the API to inject the handler + per-adapter logger label, with zero functional win. The plan’s P4 acceptance says “reuse pattern if possible” — we judge “same pattern, same shape, kept local for cohesion” as the right reading. Both queues are tested independently to keep them honest if one drifts.
  • onExit cancels in-flight requests. Codex’s adapter resolves runPromise on exit but doesn’t reject pending request promises — in Codex this is fine because turn/start is the only blocking await and its rejection is caught later. Cursor’s handshake has three sequential blocking awaits (initialize, session/new, session/prompt) any of which can hang if the child dies mid-flight. We reject every pending request on exit so the run() promise unwinds promptly; the catch block then skips the duplicate error emit via the exitErrorEmitted guard.

P6.1 — Per-boot gate token (replaces unsigned loopback POST)

Context. KiroHookServer binds 127.0.0.1 and accepts POST /kiro-hook for tool approvals. The only identification it required was the x-telecode-session header naming a SQLite session row — any local process under the same UID could forge that header and trick the daemon into approving tool actions for an unrelated session. The plan flagged this as a same-user spoof vector (§9 P6.1).

Decision. Plain shared-secret token in an Authorization: Bearer <hex> header. We considered full HMAC over the body but the threat is identity, not integrity — loopback already pins origin to the host, and integrity over plain HTTP would require TLS. 32 random bytes generated once per boot via crypto.randomBytes; the daemon, the agent JSON env, and the kiro-gate shim all hold the same hex string in memory. Constant-time compare via crypto.timingSafeEqual after a length-check sentinel (timingSafeEqual throws on length mismatch — the throw is itself timing-observable, so we early-return on length first).

File changes.

P6.2 — KiroHookServer.stop() drains in-flight asks

Context. Before this change, stop() closed the http listener and returned. Any broker.ask awaiting a Telegram tap was simply abandoned mid-await — on the kiro-cli side the hook child saw its socket vanish and returned a fail-closed deny, which is the right safety default but leaves a dangling Telegram approval message with no consequence. Worse, on a fast shutdown the SQLite store could close before the broker's pending entry was cleared, throwing on subsequent resolve() calls.

Decision. Track every in-flight request handler in a Set<Promise<void>>. stop():

  1. Flip shuttingDown so new requests receive 503 shutting down and don't enter broker.ask.
  2. Promise.race the current inflight set against a drainTimeoutMs (default 30 s; tests override to 1 s).
  3. After timeout/drain, force-close all open sockets via server.closeAllConnections() (Node ≥ 18.2) so server.close() doesn't itself hang on keep-alive sockets whose handlers are still awaiting the (now-disconnected) broker.

closeAllConnections was the surprise during testing: without it, the http close() callback only fires after all open TCP sockets close, which for our spec is "after every in-flight handler finishes" — an unbounded wait. The new sequence guarantees stop() returns within drainTimeoutMs + epsilon regardless of pending state.

File changes.

  • src/util/kiro-hook-server.ts — modified: added inflight set, shuttingDown flag, drainTimeoutMs opt; new drain race in stop(); closeAllConnections() before close().

Verification. Four new cases in tests/kiro-hook-server.test.ts: no-inflight returns prompt (< 200 ms), one in-flight broker.ask waits until manually resolved (drain unblocks on resolve, NOT before), drain timeout caps a never-resolving ask at ≈ drainTimeoutMs, and 503 for new requests after shutdown begins.

P6.3 — Daemon singleton lockfile

Context. A second daemon launched while the first is alive (typical accident: launchd StartInterval respawn during a dev npm start, or two install scripts run back-to-back) races on ~/.kiro/agents/telecode.json, both bind ephemeral hook-server ports, and both poll Telegram. The second Telegram login wins (Bot API invalidates the previous long-poll), so the first daemon goes silent but keeps writing logs — a symptom hard to diagnose from a user's vantage.

Decision. Roll-our-own lockfile at ~/.telecode/daemon.lock rather than depend on proper-lockfile (npm). Trade-off:

  • proper-lockfile is mature and handles clock skew / retries / advisory locks — but it brings in signal-exit as a transitive and ~6 KB unminified for semantics we don't need. It targets the "writer co-ordination" use case; we only need "acquire-on-boot, release-on-shutdown".
  • Rolling our own keeps the contract crystal clear — atomic create via openSync(path, 'wx') (returns EEXIST if file exists; backed by the OS-level O_CREAT|O_EXCL), PID liveness via process.kill(pid, 0). Context7-verified: on Windows, Node's process.kill(pid, 0) opens a process handle with PROCESS_QUERY_INFORMATION rather than sending a signal, returning success if the PID maps to a live process — same observable behaviour as POSIX kill -0, so no platform branch needed.

Edge cases the implementation handles: stale lockfile from a dead PID → remove + continue; malformed JSON → treat as stale; live PID matches current process (re-acquire from same daemon, no-op) → pass; live PID is FOREIGN → LockfileError with Vietnamese message naming the held PID and the lockfile path so the user can recover with kill or rm; release() refuses to delete a lockfile that was overwritten by another daemon during shutdown (PID mismatch sentinel).

File changes.

  • src/daemon/lockfile.ts — new directory + module: acquireLock(), LockfileError, isPidAlive() (exported via _internals for tests).
  • src/index.ts — modified: acquire the lock as the very FIRST side-effecting operation (before SessionStore, hook server, agent JSON), exit code 2 on conflict with the friendly Vietnamese message printed to stderr. SIGINT/SIGTERM handlers release the lock AFTER everything else has cleanly stopped, so a concurrent boot attempt during shutdown still sees the lock until the dust settles.

Verification. tests/lockfile.test.ts × 12: isPidAlive for current/dead/zero/negative/NaN PIDs; acquireLock writes correct contents, removes on release, idempotent double-release, overwrites stale (dead PID), overwrites malformed JSON, overwrites non-numeric PID, throws LockfileError when a LIVE foreign PID holds the lock (with heldByPid populated and Vietnamese message text asserted), release refuses to clobber a foreign lock (race protection), creates parent dirs via mkdir -p.

P6.4 — Cache kiro-cli --list-sessions per cwd

Design decisions (P6)

  • D-P6.1: Shared-secret token, not full HMAC. We only need identity verification, not body integrity. HMAC adds complexity (canonical serialisation, request-id replay protection) for protection against attacker capabilities our threat model doesn't admit (loopback pins origin to the host).
  • D-P6.2: closeAllConnections() after the drain race. Discovered during test development — without it, Node's server.close() callback waits for all open sockets, which for our broker-ask handlers can be unbounded. The Node 18.2+ API is exactly the right escape hatch and we have no need to support older runtimes.
  • D-P6.3: Roll-our-own lockfile. Justified by minimal-deps philosophy + the limited semantics we need (single-shot acquire, no retry loop). Documented as a deliberate trade-off so a future maintainer doesn't "improve" it by adding proper-lockfile without context.
  • D-P6.3: Friendly Vietnamese error includes BOTH PID and lockfile path. A user staring at launchd's stderr needs both pieces to recover: PID for kill, path for rm if the PID is mysteriously gone but the file remains.
  • D-P6.4: Static module-scope cache, not per-adapter field. The kiro adapter is a singleton wired via the registry, so the lifetime is "process". A module-scope Map avoids threading cache state through KiroAdapterOpts while still letting tests reset it via the _internals seam.

Doc evidence: The /cli/custom-agents/configuration-reference page shows pre/post-tool-use hooks with bodies like "{ echo \"$(date) - Bash command:\"; cat; echo; } >> /tmp/bash_audit_log" — i.e. shell brace groups + command substitution + I/O redirection. That uniquely identifies the command as “parsed by a shell”, not “invoked as a literal exec(2) argv”. The MCP server schema, by contrast, has separate command + args fields (clean exec); hooks have ONLY command.

Verdict: The hook command is a single shell-parsed string. On Windows that shell is either cmd.exe or the PowerShell instance Kiro spawns internally; either way it must be a parseable command line. The implication for Telecode is twofold:

  • Paths containing spaces (typical on Windows: C:\Program Files\Telecode\...) MUST be quoted.
  • The shebang line in our gate script (#!/usr/bin/env node) is ignored by Windows shells — we have to prepend node explicitly.

Finding #3 — Gate script invocation

Verdict: Pre-P5 the code emitted the bare absolute path (command: "/abs/kiro-gate.js"), relying on POSIX shebang resolution. On Windows that resolves to “not an executable” and the preToolUse hook fails closed for every tool call — the daemon would look like it’s alive but every Kiro tool action would error back to the model with no usable hint.

Patch applied: Introduced renderHookCommand(gateScriptPath, platform?) in src/agents/kiro-agent-config.ts with a platform branch:

  • POSIX (darwin / linux) → returns the bare path (/abs/path/kiro-gate.js) so the shebang continues to do its job; no behaviour change vs v0.8.
  • Windows ('win32') → returns node "<absolute-path>". Double-quoting handles embedded spaces; an embedded literal " in the path (rare but legal on NTFS) is escaped by doubling per the cmd.exe quoting rule.

The override is testable via the optional platform param on writeKiroTelecodeAgent({ platform: 'win32' }), so the snapshot assertions in tests/kiro-agent-config.test.ts exercise the Windows path without monkey-patching process.platform.

P5.2 — PowerShell installer (NSSM)

Context

Plan §8 P5.2 + Decision D3: user installs NSSM separately via winget (telecode does not bundle the binary). The installer must mirror install-systemd.sh ergonomics — --dry-run, env-var pre-fill for non-interactive automation, atomic file writes, hardened ACLs — and end with the daemon registered + running as a Windows service that auto-starts on reboot.

Design decisions

  • D-P5.1 NSSM over node-windows: Plan §8 already chose NSSM. We considered node-windows (pure-npm wrapper) as a zero-pre-req option but rejected it: less mature crash-restart, harder to debug from the Services snap-in, and the dependency would pull a native addon into the daemon’s production install. NSSM is one-shot install via winget and the user reuses it for any future service. Task Scheduler with OnLogon trigger is documented as a “lightweight fallback” in the README but not implemented here — no crash-restart semantics, so not equivalent.
  • D-P5.2 PowerShell 5.1 compatibility: stock Windows 10/11 ships PowerShell 5.1. We deliberately avoid ??, ?., ternary a ? b : c, and pipeline parallel (-Parallel) so users don’t have to install PowerShell 7 first. Two static-test guardrails (tests/install-windows.test.ts) lock the policy in.
  • D-P5.3 Owner-only ACL replaces chmod 600: NTFS ignores POSIX permission bits, so we set an explicit FileSystemAccessRule for the current WindowsIdentity::GetCurrent().User with SetAccessRuleProtection($true, $false) — disabling inheritance and stripping inherited ACEs. Matches the security posture of chmod 600 on POSIX.
  • D-P5.4 SIGBREAK grace window: AppStopMethodConsole = 15000 ms gives Node enough time to drain the Kiro hook server (30s default), release the lockfile, and close SQLite WAL. Without this NSSM falls through to CTRL_C_EVENT → WM_CLOSE → TerminateProcess in under 4 s by default, leaving the lockfile dirty and forcing a manual rm-after-boot cleanup. Pairs with the new SIGBREAK handler in src/index.ts (P5.3).
  • D-P5.5 Atomic file writes: System.IO.File.WriteAllText(tmp, body, UTF8NoBom) + Move-Item -Force. Move-Item with -Force overwrites atomically on the same volume; UTF-8 without BOM keeps Node’s YAML parser happy (it rejects a leading BOM in older yaml 1.x but is silent in 2.x; we go BOM-less for safety).
  • D-P5.6 Idempotent service reinstall: if the Telecode service already exists, stop + remove it before the fresh nssm install. Same posture as systemctl --user disable --now telecode.service at the top of install-systemd.sh.
  • D-P5.7 Node detection cascade: Get-Command node → %ProgramFiles%\nodejs\node.exe → %APPDATA%\nvm\v<latest>\node.exe. Three layers so the installer works on stock Node, OpenJS LTS via winget, AND nvm-windows users (the latter is the silent majority of dev hosts).

P5.3 — Source code Windows tweaks

SIGBREAK signal handler (src/index.ts)

NSSM’s graceful-stop sequence sends CTRL_BREAK_EVENT first (which Node maps to SIGBREAK), waits up to AppStopMethodConsole ms, then escalates to CTRL_C_EVENT (SIGINT) → WM_CLOSE → TerminateProcess. Without a SIGBREAK listener Node ignores the signal, NSSM falls through to the next step, and our cleanup paths (lockfile release, hook drain, SQLite close) get skipped.

Patch: one extra process.on('SIGBREAK', () => void shutdown('SIGBREAK')) line next to the existing SIGINT/SIGTERM handlers. The handler routes through the SAME shutdown closure so the cleanup contract is identical across signals. On POSIX hosts SIGBREAK isn’t a real signal — process.on silently installs a listener that never fires — so the patch is zero-cost cross-platform.

Tests: tests/windows-signals.test.ts × 4 (SIGINT/SIGTERM/SIGBREAK regression guards + shutdown closure routing invariant).

SeverityFindingPatch
[P0] NSSM’s default service identity is LocalSystem. Under that account, Node’s os.homedir() returns C:\Windows\system32\config\systemprofile — not the user’s profile. Every ~-prefixed path the daemon writes (KIRO_AGENTS_DIR → ~/.kiro/agents/telecode.json, workspace_scan roots like ~/Documents/workspaces, lockfile via TELECODE_HOME if a user kept the default) would silently target the wrong directory. kiro-cli (run from the user’s context) reads from the user’s ~/.kiro/, so the telecode agent JSON would never be picked up — preToolUse hook dead, full Kiro flow broken on Windows. Inject USERPROFILE, HOMEDRIVE, and HOMEPATH into nssm set ... AppEnvironmentExtra. Node 22 docs verified (/websites/nodejs_latest-v22_x_api): os.homedir() checks USERPROFILE FIRST on Windows before falling back to the OS profile lookup, so pinning these three env vars at install time forces the daemon — even under LocalSystem — to see the installing user’s home layout. Regression test: tests/install-windows.test.ts — “[P0 senior review] NSSM AppEnvironmentExtra injects USERPROFILE + HOMEDRIVE + HOMEPATH…”.
[P1] ACL race in Write-FileAtomic. Previous order was: write content to $tmp → Move-Item -Force to $Path → Set-FileOwnerOnlyAcl $Path. Between the rename and Set-Acl, the destination file carried the parent directory’s default ACL (typically BUILTIN\Users:RX inherited from %USERPROFILE%). A concurrent reader on the same machine — a malicious local process running under a different user, or simply a backup agent — could open .env in that window and exfiltrate the bot token. Small window, real risk on a multi-user host. Re-ordered: create empty $tmp via New-Item -ItemType File → Set-FileOwnerOnlyAcl $tmp → [System.IO.File]::WriteAllText($tmp, ...) → Move-Item -Force. The destination NEVER exists with anything other than the owner-only ACL because rename is metadata-only (same-volume case) and preserves the source ACL. The trailing Set-FileOwnerOnlyAcl $Path stays as a belt-and-braces guard for the rare cross-volume Move-Item which falls back to copy+delete. Regression test: “[P1 senior review] atomic write ACLs the tmp file BEFORE writing content”.
[P1] Lexical (not numeric) sort of nvm-managed Node versions in BOTH scripts/install-windows.ps1::Find-NodeBinary AND src/agents/kiro.ts::buildKiroMcpPath. The naive Sort-Object Name -Descending / JS [...].sort().reverse() picks v9.0.0 ABOVE v22.0.0 because "9" > "2" lexically. Real impact: a user with both Node 8 (LTS in 2018) and Node 22 still on disk (extremely common with nvm-windows / nvm-posix) would have the daemon refuse to boot with a confusing “Node too old” error even though Node 22 is installed. Replaced with a numeric semver comparator. PowerShell: Sort-Object with an @{ Expression = ... } projection that parses major*1e6 + minor*1e3 + patch as an integer. TypeScript: new compareNvmVersionsDesc(a, b) helper exported via _internalsBase and used by both Windows and POSIX branches in buildKiroMcpPath. Regression tests: 1 in install-windows.test.ts + 6 in tests/kiro.test.ts covering major/minor/patch tiebreaks, bare-major versions (v22 vs v9), and multi-version sort() ordering.
[P2] Lockfile diagnostic field host reads process.env.HOSTNAME which doesn’t exist on Windows (the equivalent is COMPUTERNAME). Always-null on Win11 hosts. Minor (the field is best-effort metadata for shared-fs scenarios, which are extremely rare for ~/.telecode/), but trivial to fix and improves observability. process.env.HOSTNAME ?? process.env.COMPUTERNAME in src/daemon/lockfile.ts::acquireLock. POSIX behaviour unchanged (HOSTNAME wins); Windows now populates the field. No new test needed — the existing lockfile tests still pass; the change is a strict-superset fallback.
