Telegram UX Widgets — Design

Companion to docs/plans/ux-telegram-widgets.html — design decisions and verification per sub-agent. Each Phase/sub-agent owns a section below, written in parallel with code.

A1 — CallbackRouter

Shared infra §3.1. Namespaced dispatcher that replaces ad-hoc bot.callbackQuery(regex) blocks. Foundation for every inline button in Tier 1/2/3 — must ship clean before any feature wiring.

Context

Existing bot wires two regex callback handlers directly in src/bot/router.ts:

  • bot.callbackQuery(/^apv:(once|always|deny):(.+)$/, ...) — approval buttons (3 actions)
  • bot.callbackQuery(/^ses:switch:(.+)$/, ...) — session quick-switch

v0.7 adds 5+ new callback families (wizard agent/project/label, project picker cd/new, pagination, etc.). Continuing the regex-per-feature pattern would scatter dispatch logic. Plan §3.1 mandates a single CallbackRouter instance that all features register against — pure additive for T3.

Requirements (from plan §3.1)

  • Chainable registration: router.on(ns, action, handler) returns this
  • Single bot.on('callback_query:data', ...) middleware installed via router.attach(bot)
  • Parse ns:action:...payload — first two segments form key, rest joined back (payload may contain :, e.g. UUIDs)
  • Unknown key → logger.warn + answerCallbackQuery() to clear loading spinner, no throw
  • Handler throws → logger.error + answerCallbackQuery({ text: '⚠️ Lỗi xử lý, thử lại sau', show_alert: true })
  • Backward compat: existing data strings apv:once:, ses:switch: must continue to dispatch
  • TS strict-mode clean, no any

Design decisions

  • Handler context type is Filter<C, 'callback_query:data'>, not CallbackQueryContext<C>. The latter type in grammY 1.43 implies a non-null ctx.match, which is only populated when registering via bot.callbackQuery(regex|str). Our router uses bot.on('callback_query:data', ...) — no match populated. Using CallbackQueryContext would force handlers to either ignore a phantom match or cast unsafely. Exported as CallbackRouterContext<C> so feature handlers can name their ctx type cleanly.
  • Defensive ack on ack-failure. If the unknown-handler or error-recovery answerCallbackQuery itself throws (e.g. Telegram API down, callback already answered), we log but never re-throw — the outer grammy bot.catch would otherwise crash the runner mid-update.
  • Generic over Context. Wizard work (Phase B3) will introduce a custom BotContext with conversation flavor; CallbackRouter<BotContext> picks that up automatically. Default param = Context keeps current callers working without changing their imports.
  • No global state. Router instance is created inside startBot() alongside the bot — matches plan constraint and lets each test spin up a fresh router with zero teardown.
  • Logger pino-style. Object-first logger.warn({ data }, 'callback_router: no handler') matches existing project convention (see src/util/logger.ts redact paths). Strings stringified via String(err) not raw err to avoid pino circular-ref issues on grammy errors.
  • Last-write-wins on duplicate keys. Re-registering (ns, action) silently overrides. Documented in JSDoc. Acceptable for in-process registration; reviewer to flag if this is ever invoked from user input (it isn't).

A2 — Conversation SQLite Storage

Shared infra §3.2. Persistent storage adapter for @grammyjs/conversations 2.1.1, backed by the project's existing better-sqlite3 instance (~/.telecode/state.db). Foundation for Phase B3 wizard's "resume across daemon restart" requirement.

Context

The @grammyjs/conversations plugin runs wizards as resumable state machines: every conversation.form.select() / conversation.wait*() call persists the conversation's logical position so a fresh process can pick up where it left off. By default the plugin uses in-memory storage — state evaporates on restart. Plan §3.2 mandates a SQLite-backed adapter that lives in the existing state.db, no new dep (Redis / Deno KV / file plugin) introduced.

Requirements (from plan §3.2)

  • Append conversation_state(key TEXT PK, data TEXT, updated_at INTEGER) to src/session/schema.sql — idempotent (CREATE IF NOT EXISTS), runs every boot
  • Export createSqliteConversationStorage(db: Database) factory returning the plugin's storage adapter
  • Prepare statements once in closure (read / write / delete) — never re-prepare per call
  • Use JSON.stringify / JSON.parse — no custom codec
  • Errors propagate (don't swallow) — callback-router (A1) handles UX
  • Survive a process restart — round-trip verified on file-backed DB

Library verification — exact adapter shape

Plan §3.2 hinted at import type { StorageAdapter } from "@grammyjs/conversations". That type name does NOT exist in 2.1.1. Read node_modules/@grammyjs/conversations/out/storage.d.ts to confirm the actual interface:

// from out/storage.d.ts
export interface VersionedState<S> {
  version: [typeof PLUGIN_DATA_VERSION, string | number];  // PLUGIN_DATA_VERSION = 0
  state: S;
}
export type MaybePromise<T> = T | Promise<T>;
export interface VersionedStateStorage<K, S> {
  read(key: K):  MaybePromise<VersionedState<S> | undefined>;
  write(key: K, state: VersionedState<S>): MaybePromise<void>;
  delete(key: K): MaybePromise<void>;
}

The plugin's conversations() options accept three storage shapes — VersionedStateStorage<string, S> (default), ConversationKeyStorage ({ type:"key", adapter, version, prefix?, getStorageKey? }), or ConversationContextStorage. A2 implements VersionedStateStorage<string, unknown>, which slots into all three.

Deviations from plan §3.2

  • Type name: StorageAdapter<unknown> → VersionedStateStorage<string, unknown>. Plan was written from memory; corrected to match shipped 2.1.1.
  • Schema location: Plan put db.exec(CREATE TABLE ...) inside the factory. SDD A2 moved it to schema.sql so the table is created exactly once at boot by SessionStore's constructor (which already .exec()s schema.sql). Adapter just db.prepare()s — no schema mutation in the hot path, no race with other consumers of the DB.
  • Read return type: Plan said "parsed JSON or undefined". Concrete type is VersionedState<unknown> | undefined — plugin then runs pinVersion(v).unpack(data) on top.

Design decisions

  • Schema separated from adapter. conversation_state table is appended to src/session/schema.sql; SessionStore already runs that file on every open via db.exec(schemaSql). Factory only prepares statements — never mutates schema. Avoids duplicate CREATE-TABLE logic and order-of-construction races.
  • Statements prepared once. The 3 db.prepare(...) calls run once in the factory closure and are reused for every read/write/delete. better-sqlite3 caches the parsed plan internally — re-using a Statement is >30% faster than re-parsing SQL each call. Matters because a wizard step writes state on every user tap.
  • JSON for serialization. VersionedState<unknown> is a plain object — JSON.stringify / JSON.parse is sufficient. No MessagePack / Buffer column. Unicode + escape-heavy payloads round-trip cleanly through SQLite TEXT (test "preserves nested + special chars" verifies 🎯 / 中文 / quotes).
  • UPSERT in one statement. INSERT … ON CONFLICT(key) DO UPDATE avoids a SELECT-then-INSERT-or-UPDATE round trip. Wizard rewrites the same key once per step — single-statement upsert minimizes lock window.
  • Errors propagate. No try/catch in the adapter. If SQLite errors (lock contention, disk full, corrupt JSON from a manual edit), the throw bubbles up to the conversations plugin, then to grammy's bot.catch, then to the CallbackRouter's outer try/catch which surfaces a Telegram alert. Adapter is a leaf — eating errors there would mask data loss.
  • Synchronous return values. better-sqlite3 is sync by design. The plugin's storage interface accepts MaybePromise<T>, so returning plain values (not Promise.resolve(...)) is fine and slightly faster (no microtask hop).
  • Adapter is storage-agnostic to wiring. Returns the raw VersionedStateStorage<string, unknown>; B4 picks the wrapper — most likely { type:"key", version:1, adapter } so a future schema break can version-bump and discard old state cleanly (per plan §2 / Risk #4).

A4 — Commands Registry & Keyboard Actions

Shared infra dữ liệu cho slash menu (§4.1), menu button (§4.3), và persistent reply keyboard (§4.2). Pure data + 1 boot helper — không phụ thuộc A1/A2/A3.

Context

Pre-v0.7 không có slash-command menu (user phải tự nhớ /session new claude foo /path). v0.7 §4.1 yêu cầu register 8 command với mô tả tiếng Việt qua setMyCommands; §4.2 yêu cầu 6 emoji-button persistent keyboard map sang slash command tương ứng; §4.3 yêu cầu chuyển nút "Menu" cạnh paperclip sang type commands để mở list trên.

Hai concern (registry-to-Telegram-API vs in-process button-to-command lookup) tách thành 2 module để tránh kéo grammy api vào hot path message:text.

Requirements (from plan §4.1, §4.2, §4.3)

  • 8 command đúng thứ tự + mô tả tiếng Việt
  • setMyCommands scope all_private_chats (bot single-user DM)
  • setChatMenuButton({ menu_button: { type: 'commands' } })
  • 6-key keyboard map với emoji prefix (chặn nhầm user gõ tay "Sessions")
  • isKeyboardActionText + keyboardActionToCommand helpers cho middleware dispatch
  • TS strict, ESM với .js suffix, không top-level side effect, không break test cũ

Design decisions

  • Tách commands-registry.ts vs keyboard-actions.ts. Registry chỉ gọi lúc boot (Telegram remote state); keyboard-actions là pure lookup chạy mỗi message:text — phải nhẹ, không kéo grammy/api dependency. Plan §6 list 2 file riêng cho cùng lý do.
  • BotCommand import từ grammy/types, không phải grammy. grammy 1.43 ./out/mod.d.ts chỉ re-export class/middleware, không re-export @grammyjs/types primitive types. Subpath grammy/types mở qua exports map (ESM-safe). Verify: import từ 'grammy' trực tiếp gây TS2305 trong typecheck — đã confirmed bằng thử nghiệm.
  • COMMANDS là readonly BotCommand[] để immutable shared state. Cast as BotCommand[] chỉ 1 chỗ duy nhất ở callsite setMyCommands vì grammy Other<...> wrapper tinh chỉnh signature qua mapped types.
  • Emoji prefix là contract. Key map dùng "📋 Sessions" thay vì "Sessions" — chặn false-positive khi user gõ tay "Sessions". isKeyboardActionText dùng Object.prototype.hasOwnProperty.call thay vì in operator hoặc obj[key] !== undefined để chặn prototype-pollution (vd literal "toString" sẽ không match thành function reference). Object.freeze map để runtime mutation cũng được chặn.
  • Ordering: setMyCommands → setChatMenuButton. Reverse order sẽ làm menu button briefly show stale commands. Test assert ordering qua invocationCallOrder.
  • Test ở tests/ thay vì co-located. Spec task nói src/bot/commands-registry.test.ts nhưng vitest.config.ts hiện glob tests/**/*.test.ts. Co-located sẽ không chạy. Đặt tại tests/commands-registry.test.ts theo convention hiện hành. Tài liệu deviation tại đây để tránh confusion sau này.

A3 — ReplyBuilders

Shared infra §3.3. Pure factory functions that produce { text, reply_markup } payloads used by Tier 2 handlers (/sessions, /projects) and the Tier 1 persistent reply keyboard. Each builder accepts extraButtons so T3 features (follow-up suggestions, allow-always) can append rows without touching the builder.

Context

Pre-v0.7 the only inline keyboard helpers lived in src/bot/keyboards.ts (approvalKeyboard, sessionPickKeyboard). They returned just a keyboard — text was constructed ad-hoc in each command handler, often as concatenated row.label + ' ' + row.status strings with no shared formatting (relative time, agent badge, active marker were copy-pasted).

v0.7 §5.2/§5.3 introduces list views (sessions, projects) with structured rendering: active marker, agent icon, relative time, pagination. These must be reusable from Tier 2 handlers and from T3 features that re-render the same list with extra follow-up buttons. A single factory module is mandated by plan §3.3.

Requirements (from plan §3.3, §4.2, §5.2, §5.3)

  • buildPersistentKeyboard() — 6 buttons in 3 rows of 2: Sessions / Projects / Status / Stop / Screen / Help, resized + persistent
  • removeKeyboard() — returns Telegram ReplyKeyboardRemove markup for wizard entry
  • buildSessionList(sessions, activeId, extraButtons?) — active marker ●, agent icon (🤖/⚡), relative time, switch-button per session + [➕ New session] row
  • buildProjectList(projects, opts?) — 2 buttons per project (Switch + New), pagination at 8/page when total > perPage
  • All builders pure — no I/O, no logger, no bot ref. Deterministic given inputs.
  • extraButtons: InlineKeyboardButton[][] param so T3 can append follow-up rows
  • Callback data ≤ 64 bytes (Telegram hard limit) — risk register §9 item 1
  • ESM strict TS, .js suffix on relative imports

Design decisions

  • Full UUID in session:switch:<id>, not 8-char prefix. A UUID v4 is 36 bytes; session:switch: prefix is 15 bytes → 51 total, well under 64. Truncating to 8 chars (~3.4 × 10⁹ keyspace) is gratuitous collision risk for zero byte savings. Test asserts Buffer.byteLength(data) < 64 with realistic UUID input.
  • Integer project_id stringified directly. project:cd:999999 = 18 bytes — no UUID needed, the table uses AUTOINCREMENT INTEGER per src/session/schema.sql. Test covers 6-digit id.
  • Relative time boundaries match plan mock exactly: <60s → "just now", <60m → "Xm ago", <24h → "Xh ago", else "Xd ago". Floor (not round) so a session 2.7 min old reads "2m ago" — matches Telegram client conventions. Future timestamps clamp to "just now" defensively (clock skew during daemon restart).
  • Active marker uses 2-space indent for inactive rows (" label") so the bullet/space column width is stable across the list — visually consistent in a monospace-ish chat font. Plan mock uses 2 spaces; preserved exactly.
  • No leading-empty-row pollution. grammY's new InlineKeyboard() starts with seed row [[]]. Naive .text().row() loops leave a trailing empty row, throwing off row-count assertions. Builders use first-flag pattern (if (!first) kb.row();) to break before adding the next row only after the first item, keeping the row count exactly equal to the visible button count.
  • Pagination clamps out-of-range pages (Math.min(totalPages, Math.max(1, page))) — defensive against stale callback_data from old messages after a project was deleted. Test covers page: 0 and page: 99.
  • Path shortening: shortenPath('/Users/koi/workspaces/foo') → "…/workspaces/foo". Keeps the last 2 path components so users still recognize the project without the home-dir noise; one-line static helper, no os.homedir() branching needed.
  • Empty-list hint for projects ("(no projects registered yet — use /project register)") because an empty inline keyboard would render nothing actionable on mobile. Sessions don't need this — the [➕ New session] button is always present.
  • Builders return InlineKeyboard instance (not raw array). Lets handlers chain extra rows post-construction if needed, and lets grammY serialize directly via its own toJSON. The ReplyPayload.reply_markup type is intentionally narrowed to InlineKeyboard — list builders never produce a reply (custom) keyboard.
  • Pagination indicator is a no-op button (callback_data: 'project:page:current') so the layout stays symmetric (prev / page X/Y / next) without needing Telegram-side disabled-button support (which doesn't exist). The router will dispatch this to a no-op handler that just answerCallbackQuery().

B1 — /sessions Command Handler

Feature wiring §5.3 — first Phase-B consumer of A1 (CallbackRouter) + A3 (ReplyBuilders). Adds a new top-level /sessions command that surfaces the enhanced list view (active marker, agent badge, relative time, inline switch buttons, [➕ New session] entry) without disturbing the legacy /session list subcommand or any other approved flows.

Context

Design decision — ses: vs session: namespace

A1 ships router.on('ses', 'switch', handler) matching the legacy ses:switch:<id> callback_data emitted by sessionPickKeyboard(). A3 ships buildSessionList which emits session:switch:<id> (full word). These collide on action name but differ on namespace — a Telegram callback_query carries one literal string, so the router must register both.

Choice: standardize new code on session: (full word, more readable, matches the session:switch / wizard:new-start family for consistency), AND keep ses:switch registered as a backward-compat alias bound to the same handler closure.

Why both, not migrate-and-delete:

  • Old messages already approved by the user (sitting in their Telegram history) contain literal ses:switch:<uuid> in their callback_data. Telegram does not let the bot rewrite that data after the fact. Deleting the ses:switch route would turn every old tap into a "no handler" warn + silent ack.
  • /session list (still emitting sessionPickKeyboard) is explicitly preserved by the task brief. Even if we wanted to delete the legacy ns, we'd still need it in-process — leaving the alias makes that future cleanup a pure single-line removal once the keyboard helper is retired.
  • Both routes resolve to the same closure (switchSessionHandler), so there is no behavior drift or maintenance burden — the only thing the router sees is two map entries pointing to the same function.

Implementation lives in src/bot/router.ts; the closure is declared once with the existing Parameters<Parameters<typeof callbackRouter.on>[2]>[0] pattern (same trick used by resolveApproval in A1) so we don't have to import CallbackRouterContext.

Design decisions (other)

  • New command, not refactor of /session list. The subcommand still emits the old keyboard and is left untouched — task brief requires "all existing 81 tests must still pass" and gives explicit guidance "leave it alone". Future deprecation is a separate decision once /sessions proves out in production.
  • Conditional parse_mode spread. A3's buildSessionList never sets parse_mode today (the list uses plain text on purpose — labels can contain underscores that would break Markdown). But the ReplyPayload interface declares parse_mode?, so the handler spreads it conditionally rather than passing undefined explicitly — keeps the reply options object clean and lets a future builder opt into HTML/Markdown without changing the handler.
  • Placeholder for wizard:new-start. B3 will replace this with ctx.conversation.enter('newSession'). For B1 the handler just answerCallbackQuery() (clears the spinner) and replies with a one-liner pointing users at the textual fallback (/session new ...). This keeps the [➕ New session] button from being a dead click during the gap between B1 and B3 ship.
  • No new tests for the router alias. The router itself is exhaustively tested by A1 (parses ns:action correctly, payload remainder preserved, etc.). Adding a router-integration test for the alias would duplicate that coverage. The B1 command test covers the only behavior B1 actually introduces (handler output for the /sessions command).

B2 — /projects Picker with Pagination

Context

The old /projects handler emitted a plain Markdown list with no actionable buttons — users had to type /cd <name> separately to switch. B2 refactors the command to use buildProjectList (A3) and wires three new project:* callback handlers on the existing CallbackRouter (A1) so each project gets one-tap Switch + New session here + a pagination nav row when projects > 8.

Plan reference: §5.2 of docs/plans/ux-telegram-widgets.html. Depends on A1 (router) + A3 (builder). The B3 wizard will replace this file's projectNewHandler placeholder with the real conversation entry.

Requirements (from plan §5.2)

  • Replace the plain-text /projects reply with the inline picker emitted by buildProjectList, starting on page 1.
  • Wire project:cd:<id> → set the chat's active project via SessionStore.setActiveProject; reply 📁 Active project → `name`; strip the inline keyboard from the originating message.
  • Wire project:new:<id> → for B2 only, ack + placeholder reply ("Wizard /new sắp ra mắt với project đã chọn"). B3 will replace this with a wizard entry pre-filling the chosen project.
  • Wire project:page:<n> → re-render via ctx.editMessageText using buildProjectList(items, {page: N}). Out-of-range pages already clamped by the builder.
  • All existing tests continue to pass; new tests cover the command + each callback handler against a real in-memory SessionStore.

Design decisions

  • Extract callbacks into src/bot/callbacks/projects.ts rather than inlining them in src/bot/router.ts. Reasons: (a) the handlers can be unit-tested without booting grammY's runner, mirroring how registerCommands is structured; (b) router.ts stays focused on wiring + cross-cutting concerns (approvals, session switch, wizard entry); (c) B3 will replace projectNewHandler with a wizard entry pre-filling the project — keeping the project callbacks together makes that a single-file change.
  • Lazy listProjects() snapshot per callback. The page handler re-reads the projects table on every tap so a newly registered project shows up immediately without bot restart. Cost is negligible (single indexed SQLite read; ORDER BY name).
  • project:cd also retargets the active session's project_id when one exists — matches the /cd command's existing semantics in commands/index.ts. Without this, the next prompt would still execute under the previous project's cwd, surprising the user.
  • Strip keyboard via editMessageReplyMarkup({ reply_markup: undefined }) after a successful project:cd instead of editing text. We keep the project listing visible (still useful as a reference) but kill the button cluster — switching is a one-shot action, re-taps would be no-ops.
  • Swallow only "message is not modified" errors in project:page. Any other failure (auth, network) is surfaced via logger.warn. The "not modified" case arises when Telegram's text+markup hash matches the existing message (e.g. double-tap on the same nav button) — harmless.
  • Defensive Number.isInteger(id) && id > 0 validation on every payload before any DB lookup. Telegram clients honor what we send, but a stale/edited callback could still arrive with garbage; reject it explicitly rather than letting NaN reach SQLite.
  • Backward-compat: the legacy /cd <name> text command in commands/index.ts is untouched. Existing scripts / muscle memory keep working.

Store API used

  • SessionStore.listProjects() — sorted ORDER BY name; returns full ProjectRow[], we project to {id, name, path}.
  • SessionStore.getProject(id) — id lookup; returns undefined for unknown.
  • SessionStore.setActiveProject(chatId, id) — upserts into chat_state.
  • SessionStore.getChatState(chatId) — read active_session_id so we can retarget the session's project_id.
  • SessionStore.updateSession(id, { project_id }) — used by the active-session retarget path.
  • SessionStore.upsertProject(name, path) — only used by the tests to seed fixtures.

API contract — @grammyjs/conversations 2.1.1 (verified live in node_modules)

// Outer middleware flavor
export type BotContext = ConversationFlavor<Context>;

// Plugin install (must be BEFORE registerCommands so ctx.conversation exists in handlers)
bot.use(conversations({
  storage: {
    type: 'key',                       // disambiguator for ConversationKeyStorage
    version: 1,                        // bump → wipes stale wizard state
    adapter: createSqliteConversationStorage(deps.store.db),
  },
}));

// Register the conversation. Deps curried via closure → wizard stays mock-friendly.
bot.use(createConversation(
  (conversation: Conversation, ctx: Context) => newSession(conversation, ctx, { store, manager }),
  'newSession',     // explicit id since the wrapped fn is anonymous
));

// Entry point
bot.command('new', async (ctx) => { await ctx.conversation.enter('newSession'); });

Inside the wizard the supported calls are:

  • conversation.waitFor('callback_query:data') — type-narrowed to CallbackQueryContext<C>. Used for all 3 inline-button steps.
  • conversation.form.text({ otherwise }) — wait for plain text; otherwise fires when the next update is not a text message (we do regex validation manually after).
  • conversation.external(() => ...) — side-effects (DB reads/writes); the plugin memoizes the result so it's not re-executed on replay.

Design decisions

  • Deps via closure curry, not module-level singleton. Trade-off: createConversation receives an anonymous fn so we must pass 'newSession' as the explicit id (the plugin defaults to fn.name). Win: newSession() is a plain async function — unit-testable with mock conversation handles, no global state.
  • Callback handling lives INSIDE the wizard, not on CallbackRouter. The conversations plugin intercepts callback_query:data updates whenever a conversation is active for the chat. wizard:new-* data never reaches the outer router. The router still registers wizard:new-start as a thin entry point for the [➕ New session] button taps from outside the wizard.
  • Label validation manual, not form.select. Regex /^[a-zA-Z0-9_-]{1,40}$/ is too unbounded for select (which needs a finite list). Loop-on-invalid + explicit "/cancel" sentinel is simpler and matches plan §5.1 step 4 verbatim. Duplicate-label check (via store.findSessionByLabel wrapped in external) added defensively so createSession doesn't surface an opaque SQLite UNIQUE error.
  • No force_reply on the label-step prompt. Reason: force_reply works against persistent reply keyboards (it would re-show that keyboard mid-wizard), and it requires us to track the prompt's message_id for the "reply to which?" UX which adds branching. The plain text prompt is unambiguous because the conversation has already removed all interactive surfaces. B4 will (separately) remove + restore the persistent reply keyboard around wizard entry/exit.
  • Pagination at PROJECTS_PER_PAGE = 8. Re-renders via cbCtx.editMessageText on the existing wizard message — no message-id tracking needed because grammY's CallbackQueryContext.editMessageText auto-targets the message the button was attached to.
  • Back at step 2 = abort + restart hint, not in-place re-render of step 1. Implementing real "back" requires conversation.checkpoint() + conversation.rewind() dance; plan §5.1 explicitly allows "simpler — just cancel and restart". Saves ~50 LoC for a flow users rarely traverse.
  • No projects registered → graceful abort. Plan §5.1 always shows a picker; if the picker is empty there's nothing to render. Bail with hint to /add rather than fabricate a "no project" sentinel button.
  • conversation.external wraps EVERY DB call — listProjects(), findSessionByLabel(), manager.createSession(), setActiveSession(). Plugin replay semantics: anything outside external runs on every resume. Without this wrap, a daemon restart mid-wizard would create the same session N times.
  • Wizard-new-start (button-tap entry) reused: [➕ New session] button on the /sessions list now calls ctx.conversation.enter('newSession') (was a placeholder reply). Same flow as /new. Throws are caught and surfaced as "wizard already running".
  • session:list-trigger / session:logs-trigger rendered on the wizard's success message are T3 stubs — for now they just answerCallbackQuery with a hint to use /sessions or /status logs. Plan §5.1 step 5 explicitly defers their real handlers to T3.

B4 — Boot wiring

Final connect step. Hooks up A1–B3 surfaces (CallbackRouter, conversations storage, commands registry, keyboard-actions map, reply-builders, wizard) to the running Bot instance inside startBot() so the user gets the v0.7 UX end-to-end.

Context

Through B3, the codebase shipped the building blocks but the runtime bot did not actually expose them:

  • No call to applyCommandsAndMenu(bot) → Telegram slash menu still showed the pre-v0.7 list and the chat menu button defaulted to the paperclip.
  • No persistent reply keyboard attached to any message → users had to type commands manually.
  • No middleware translating reply-keyboard taps ("📋 Sessions") into slash commands → the 6-button UX would have been dead.
  • bot.command('help', ...) missing despite being listed in the registry → tapping Help in the slash menu would yield no response.
  • Wizard exit did not restore the keyboard explicitly (B3 deferred this to B4).

B4 closes all five gaps with a focused router.ts edit and 2 small touches elsewhere.

Requirements (from plan §4.1, §4.2, §5.1)

  • Call applyCommandsAndMenu(bot) at boot, idempotent; failures must NOT block boot.
  • Send the 6-button persistent keyboard on /start so the user has tap-to-command access immediately.
  • Translate reply-keyboard taps into slash commands BEFORE downstream command middleware runs; SKIP translation while a wizard conversation is active (wizard owns input).
  • Register a /help command (listed in registry; must have a handler).
  • Restore the persistent keyboard on wizard exit; per plan §4.2 the keyboard may be hidden during the wizard, restored after.

Design decisions

  • applyCommandsAndMenu in try/catch after run(bot). Telegram API transient failures (network blip during boot) should NOT prevent the bot from accepting updates. Slash menu sync is cosmetic discovery surface; commands still work via typed input or persistent keyboard. Failure logged at WARN level, never thrown. Subsequent reboots retry idempotently.
  • Keyboard-action middleware mutates ctx.update.message.text. Simplest path the plan calls out: rewrite the raw update before bot.command(...) middleware re-parses it. Alternative (calling the command handler directly) would bypass other middlewares (whitelist, logging) and would skip ctx population logic — riskier. Mutation is safe because each Update is processed exactly once per ctx and we own this object exclusively.
  • Skip-when-conversation-active uses ctx.conversation.active(). Plugin-2.1.1 API returns Record<name, count>; we sum values to detect "any conversation running in this chat". This prevents the keyboard from hijacking the label-step text input (e.g. user types "📋 Sessions" as a literal label).
  • Generic applyCommandsAndMenu<C extends Context>. Bot<C> is invariant in C in grammY; without a type parameter, callers using a custom flavor (here Bot<BotContext>) get TS2345 on the call. Function only reads bot.api — the context flavor is irrelevant to the implementation.
  • Wizard keyboard UX — KEEP persistent keyboard visible during wizard. Per plan note "khi vào wizard, keyboard tạm ẩn" + task constraint "be conservative... when in doubt KEEP persistent keyboard visible": Telegram allows only one reply_markup per message, so hiding the keyboard at wizard entry would either require an extra "wizard mode" notice message (UX noise) or replacing the inline keyboard markup. Persistent keyboards do NOT interfere with inline buttons — both render side-by-side on Telegram clients. We accept that the persistent keyboard remains visible during the wizard; the middleware already defers to ctx.conversation.active(), so accidental taps are no-ops (the literal text reaches the wizard's form.text() and fails label validation, looping with a hint).
  • Wizard exit — separate trailing message with keyboard restore. On success the wizard already sends a message carrying the inline [Switch khác] [Tail logs] markup. Because Telegram allows one reply_markup per message, the keyboard restore lives in a second tiny "✓ Sẵn sàng nhận prompt" message with reply_markup: buildPersistentKeyboard(). Cost: one extra message per successful wizard exit. Wrapped in try/catch so a transient failure doesn't crash the wizard — user's next /start would re-attach the keyboard anyway.
  • /help in router.ts, not commands/index.ts. The handler doesn't need CommandDeps (no store/manager/policy access — pure static text). Placing it inline alongside /new keeps the wiring layer self-contained: every command that's listed in the registry has a visible handler in router.ts.
