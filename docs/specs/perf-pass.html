Perf pass — giảm độ trễ telecode vs CLI trực tiếp

Người dùng cảm nhận telecode chậm hơn chạy CLI trực tiếp. Điều tra xác nhận đúng. Spec này gom các quick-win độ-trễ rủi-ro-thấp + instrument để đo, đồng thời gỡ regression responsiveness do fix done-summary (D1) gây ra. Áp dụng cho cả 4 AI agentic (Claude · Kiro · Codex · Cursor) vì nằm ở tầng dùng chung. Root-cause structural (spawn lại process mỗi turn) được tách sang spec riêng warm-session.

Slug · perf-pass Author · vendor.01@frt.vn Date · 2026-05-22 Effort · ~0.5–1 ngày Status · Implemented · pending senior review

TL;DR

Tách chậm cảm nhận vs chậm thật. Perf pass xử 3 thứ rẻ-mà-hiệu-quả: (A) hạ debounce streaming 3000ms → adaptive ~800ms; (C) auto-done-summary non-blocking (không gây "session busy") + recap rẻ cho mode đã stream text (chỉ mode summary mới gọi LLM thật) — gỡ thuế perf mà fix D1 vừa thêm; (I) instrument đo spawn→first-token→result mỗi turn để định lượng.

Root-cause thật (B) — query() string-mode tạo process mới + --resume replay mỗi turn (SDK docs: "each call starts fresh"), chi phí tăng theo độ dài phiên — KHÔNG nằm trong spec này; nó là refactor lớn → spec warm-session riêng. Instrument (I) ở đây chính là dữ liệu đầu vào để quyết B.

Design Approval gate #2

Hoàn thiện chi tiết song song khi implement (DAG). Nháp định hướng.

A — Adaptive debounce (R1)

notifier.ts: hạ DEFAULT_DEBOUNCE_MS 3000→800 + config.ts default tương ứng. Thêm flush sớm: nếu buffer "đứng yên" > ~250ms (không có append mới) thì flush ngay thay vì chờ trọn cửa sổ. Trần edit-rate vẫn qua takeToken() nên không vỡ 429. Giữ ROTATE_* nguyên.

C1 — Summarize non-blocking (R2)

Hiện summarize chạy fire-and-forget nhưng acquire busy-mutex qua manager.dispatch → prompt user mới bị reject. Hướng: đánh dấu summarize là "low-priority/cancellable" — khi dispatch nhận prompt user mới mà mutex đang bị giữ BỞI summarize, thì hủy summarize (abort) và nhường cho user, thay vì trả "session busy". Cần phân biệt chủ thể giữ mutex (user vs summarize) — thêm cờ rt.holder: 'user'|'summarize'|null.

C2 — Recap rẻ cho mode đã stream (R3)

Trong nhánh done: nếu !textWasSuppressed (normal/thinking/verbose — user đã thấy full text), KHÔNG gọi summarizeWithSession. Thay vào đó dựng recap rẻ từ dữ liệu sẵn có (tail của turnText + kết quả tool cuối + cost/duration) — 0 round-trip. Chỉ khi textWasSuppressed (summary mode) mới gọi LLM summarize như hiện tại. Giữ nguyên guaranteed-content fallback §D4.

I — Instrumentation (R4)

Thêm timing log (level 30, gắn sessionId): t_prompt_received, t_dispatch_start, t_first_text, t_done; suy ra spawnToFirstTokenMs, firstTokenToDoneMs, totalMs, + resumeContextChars (độ dài context replay, để thấy nó tăng theo phiên). Gắn ở manager.dispatch + adapter. Đây là dữ liệu quyết định warm-session.
