Spec · Telecode v1.4

AskUserQuestion answer routing

AskUserQuestion hiện chỉ render đẹp lên Telegram nhưng không thật sự hỏi user — SDK nhận lại answers = {} tự động, Claude tiếp tục bằng giả định. Spec này wire một vòng câu hỏi → trả lời thực sự thông qua inline keyboard + reply, dùng đúng cơ chế chính thức canUseTool ⟶ updatedInput.answers của Claude Agent SDK.

Slug · askuserquestion-answer-routing Author · vendor.01@frt.vn Date · 2026-05-31 Effort · ~1 ngày Status · Implemented · Pass 1 senior review APPROVED · ready for security scan + commit SDK · @anthropic-ai/claude-agent-sdk@0.3.145

TL;DR

Bug: canUseTool trong src/agents/claude.ts:46 đối xử AskUserQuestion như tool thường → đi qua PolicyEngine → broker hỏi Allow / Deny tool (3 nút), KHÔNG bao giờ thu thập câu trả lời thực. Sau khi user "Allow", SDK forward call về backend, nhận answers rỗng → Claude đoán bừa.

Fix: special-case AskUserQuestion tại canUseTool. Hiển thị câu hỏi + inline keyboard option-per-button trên Telegram, suspend handler, đợi user tap nút (hoặc reply text cho "Other"), rồi trả về { behavior: 'allow', updatedInput: { questions, answers } } theo schema chính thức AskUserQuestionInput.answers (Context7 verified, SDK sdk-tools.d.ts:2137-2139).

Không cần MCP server riêng, không cần inputAlias. Cơ chế updatedInput.answers đã là path chính thức của SDK. Toàn bộ thay đổi nằm trong process bridge, không phá compatibility với policy/broker hiện có cho các tool khác.

Context

Telecode là daemon bắc cầu Telegram ↔ Claude Agent SDK (kèm Codex / Kiro adapter). Mỗi session trong src/agents/claude.ts chạy query() với một canUseTool callback duy nhất — đây là policy gate cho mọi tool call.

Mô hình permission hiện tại:

  1. policy.decide(toolName, input) tra YAML allow/deny (file path/command glob).
  2. Nếu rule là 'allow' hoặc 'deny' → trả luôn.
  3. Còn lại ('ask') → ApprovalBroker.ask() hiện 4 nút trên Telegram: Allow once · Allow always · Forever · Deny.

Hệ quả lên AskUserQuestion: tool này không được khai báo trong policy.yaml → mặc định 'ask' → broker chỉ hỏi quyền chạy tool, KHÔNG bao giờ surface câu hỏi nội dung mà Claude muốn user trả lời. User tap "Allow once" → canUseTool trả { behavior: 'allow', updatedInput: input } giữ nguyên input, SDK forward call lên backend, không có nguồn answer nào → tool_result rỗng → Claude tiếp tục bằng giả định.

Spec tiền nhiệm telegram-message-chunking-fix.html đã sửa render (câu hỏi hiện đầy đủ qua sendChunked) nhưng explicit out-of-scope phần routing answer ("surfacing blocking asks regardless of mode is a separate feature decision. Recommend a follow-up spec."). Đây chính là follow-up spec đó.

Requirements

Approval gate: ngoài tài liệu (portal hoặc agent prompt).

  • R1 — User thực sự được hỏi. Khi Claude gọi AskUserQuestion, Telegram hiển thị từng câu hỏi + nút bấm cho từng option. User tap nút = chọn option đó.
  • R2 — Câu trả lời quay về Claude đúng schema. Sau khi user trả lời xong tất cả câu hỏi trong batch (SDK cho phép 1–4), Telecode return { behavior: 'allow', updatedInput: { questions, answers } } với answers là record question text → label đúng schema AskUserQuestionInput.answers.
  • R3 — Hỗ trợ multi-select. Question có multiSelect: true → keyboard toggle nhiều nút, có nút "✅ Done" để confirm. Answer trả về dạng comma-separated theo convention SDK.
  • R4 — Hỗ trợ free-text ("Other"). Nếu user muốn trả lời ngoài options: nút "✏️ Other" → bot reply "Trả lời tự do cho câu: …" + đợi text reply (dùng force_reply). Free-text dùng làm answer label.
  • R5 — Multi-question batch. Một AskUserQuestion có thể chứa 1–4 câu. Phải trả lời lần lượt từng câu trước khi resolve toàn batch. UI cho user biết "Câu N/Total".
  • R6 — Timeout an toàn. Nếu user không trả lời trong N phút (config, default 10 phút), canUseTool trả { behavior: 'deny', message: 'user did not answer within timeout' } để Claude biết và dừng thay vì đoán bừa. Telegram báo "⌛ Timeout".
  • R7 — Không loop qua PolicyEngine/ApprovalBroker. AskUserQuestion KHÔNG còn nhả 4-nút Allow/Deny — vì việc "hỏi user" là chính nó. Special-case sớm trong canUseTool.
  • R8 — Không regression. Tool khác (Read/Edit/Bash/...) giữ nguyên đường PolicyEngine + ApprovalBroker. Test cũ pass 100%. Spec render hiện tại (renderAskUserQuestion, sendChunked dispatch) vẫn được tái sử dụng cho phần "show question text", chỉ thêm reply_markup.
  • R9 — Session focus an toàn. Khi AskUserQuestion gọi từ background session, auto-switch active session sang nó (giống pattern broker.ask hiện tại) — user không bị mất context.
  • R10 — Concurrency. Hai session khác nhau cùng raise AskUserQuestion phải không trộn lẫn câu trả lời. Pending entry key theo (sessionId, toolUseID).
  • R11 — Adapter-generic module. AskQuestionBroker + AskPrompter phải tách khỏi claude.ts-specific code. Nếu sau này adapter khác (Codex, Kiro, hoặc adapter mới) phát hiện ra tool/protocol-message yêu cầu user trả lời từ option set → cần reuse được module này chỉ bằng cách inject thêm 1 wiring point ở adapter đó. Cụ thể, Claude adapter wire trong canUseTool; Codex (nếu protocol bổ sung) wire trong message dispatch; Kiro (nếu CLI hỗ trợ) wire trong preToolUse hook. Spec scope hiện chỉ implement cho Claude (vì chỉ Claude SDK 0.3.145 có tool AskUserQuestion); Codex/Kiro out-of-scope code path nhưng module API design phải accommodate.

Design

Approval gate: ngoài tài liệu. Verify Context7 đã chốt schema; chi tiết được điền song song khi implement (rule §2).

D1 — Special-case AskUserQuestion trong canUseTool

Tại src/agents/claude.ts:46, thêm branch sớm:

const canUseTool: CanUseTool = async (toolName, input, options) => {
  if (toolName === 'AskUserQuestion') {
    return await askBroker.askQuestion({
      sessionId: start.sessionId,
      chatId: start.chatId,
      sessionLabel: start.sessionLabel,
      toolUseID: options?.toolUseID ?? randomUUID(), // correlation key
      input: input as AskUserQuestionInput,
    });
  }
  // ... existing PolicyEngine + ApprovalBroker path
};

askBroker.askQuestion(...) trả về PermissionResult đúng shape SDK: { behavior: 'allow', updatedInput: { questions, answers } } hoặc { behavior: 'deny', message } khi timeout.

D2 — AskQuestionBroker (module mới, src/approval/ask-broker.ts)

Tách module riêng (không nhét vào ApprovalBroker) vì semantic khác: trả về answer record, không phải allow/deny scalar.

  • API: askQuestion(req): Promise<PermissionResult> — suspend Promise đến khi resolveAnswer(toolUseID, answers) hoặc cancelAnswer(toolUseID) hoặc timeout.
  • State: Map<toolUseID, PendingAsk> chứa { req, resolve, timer, answers: Partial<Record<string, string|string[]>>, currentQuestionIdx, anchorMessageIds[] }.
  • Prompter attach pattern giống ApprovalBroker: attach(p: AskPrompter) với p.prompt(req) / p.notifyTimeout(req) / p.editAnswered(req, q, answer).
  • Timeout: settings.askTimeoutMs, default 10 phút. Khi timeout: resolve({ behavior: 'deny', message: 'user did not answer within timeout' }), prompter edit tin nhắn câu hỏi thành "⌛ Timeout — Claude sẽ tiếp tục mà không có câu trả lời".

D3 — Telegram UI: inline keyboard + multi-question state machine

Tái dụng renderAskUserQuestion hiện có để compose body text (đã chunk-safe sau v1.3). Bổ sung reply_markup:

  • Single-select: mỗi option = 1 nút riêng dòng (option label ngắn ≤24 chars Telegram), callback_data = ask:pick:<toolUseID>:<qIdx>:<oIdx>. Thêm nút "✏️ Other" (ask:other:<toolUseID>:<qIdx>) và "✖ Cancel" (ask:cancel:<toolUseID>).
  • Multi-select: nút có prefix ☐/☑ phản ánh state. Tap = toggle (edit message giữ keyboard). Thêm nút "✅ Done" (ask:done:<toolUseID>:<qIdx>) để confirm.
  • Multi-question: sau khi câu N được trả lời → edit tin nhắn câu N thành "✓ question → answer" (read-only, gỡ keyboard) → render câu N+1 với keyboard mới. Header câu hiện tại có badge "Câu 2/4".
  • Khi tất cả N câu xong → resolveAnswer(toolUseID, answers) → canUseTool trả về SDK.

D4 — Callback router wire

Đăng ký 4 namespace mới trong CallbackRouter (đường convention ns:action:payload, src/bot/callback-router.ts): ask:pick, ask:other, ask:done, ask:cancel. Handler giải payload → lookup pending toolUseID trong AskQuestionBroker → mutate state hoặc resolve. answerCallbackQuery với feedback ngắn ("Đã chọn: X").

D5 — "Other" / free-text flow

User tap "✏️ Other" → bot sendMessage "Trả lời câu 'question' (reply tin này):" với reply_markup: { force_reply: true, selective: true }. Lưu pending (chatId, replyToMessageId) → (toolUseID, qIdx) vào askBroker.pendingFreeText. Trong bot.on('message:text') handler, BEFORE call dispatchPromptToActiveSession, check nếu ctx.message.reply_to_message?.message_id match pending free-text → consume nó làm answer thay vì forward prompt.

D6 — Tránh PolicyEngine/ApprovalBroker cho AskUserQuestion (R7)

Vì branch ở D1 return sớm, không bao giờ đến policy.decide(...) hay broker.ask(...) cho tool này. Side effect:

  • Log policy/audit: thêm store.logTool({ tool_name: 'AskUserQuestion', decision: 'user_answered:<summary>' }) trong askBroker resolve để giữ audit trail.
  • Không cần update policy.example.yaml.

D7 — Background session auto-switch (R9)

Tận dụng createApprovalPrompter's auto-switch helper (runAutoSwitch trong router.ts). Refactor nhẹ: extract runAutoSwitchForChat(chatId, sessionId) ra shared util để AskPrompter cũng gọi được. Không thay đổi logic, chỉ tách re-use.

D8 — Concurrency (R10)

toolUseID SDK cung cấp là unique per call (UUID). Pending Map key bằng nó → 2 session raise đồng thời cũng không đụng nhau. Callback_data đã embed toolUseID. Free-text reply lookup theo replyToMessageId → cũng unique.
