Long-message chunking + AskUserQuestion render fix

Response dài (truyện, summary, code output) bị cắt cụt im lặng ở 3500 ký tự; AskUserQuestion bị truncate trong từng câu hỏi nên đọc không hiểu. Sửa để mọi nội dung dài được chia nhiều tin nhắn thay vì clip().

Slug · telegram-message-chunking-fix Author · vendor.01@frt.vn Date · 2026-05-22 Effort · ~nửa ngày Status · Implemented · in senior review

TL;DR

Bug 1 — Response dài bị cắt. Streaming flush() trong notifier.ts tích toàn bộ text vào s.buffer nhưng clip(composed) chỉ giữ 3500 ký tự đầu. Khi rotate, buffer KHÔNG bị trim → mỗi flush vẫn re-clip đúng 3500 ký tự đầu → phần >3500 mất vĩnh viễn. Fix: rotate thật — commit chunk đầy rồi mang phần dư sang message mới (live-edit tiếp), không clip.

Bug 2 — AskUserQuestion cụt. renderAskUserQuestion() hard-truncate desc=300/body=3000 + "…", rồi gửi qua sendPlain() → clip() lần 2 ở 3500. Fix: render đầy đủ + gửi AskUserQuestion qua sendChunked() (bypass burst-collapse).

Tận dụng hạ tầng sẵn có: splitForTelegram() + sendChunked() đã tồn tại và đúng. Bug là các đường gửi chính không gọi chúng. Không thêm dependency mới.

Design

Approval gate 2 — sẽ hoàn thiện song song code

D1 — Streaming overflow rotation (notifier flush())

Thay vì clip(), khi composed.length > MAX_MSG_CHARS:

  1. Gọi splitForTelegram(composed) → parts[].
  2. Commit các phần parts[0..n-2] thành tin nhắn hoàn chỉnh: edit messageId hiện tại = parts[0]; gửi parts[1..n-2] bằng sendMessage mới (silent giữ nguyên).
  3. Carry phần cuối parts[n-1]: đặt làm buffer sống mới — s.buffer = parts[n-1], s.messageId = null (flush kế sẽ tạo tin mới rồi edit-in-place tiếp), reset edits/charsSinceRotate/startedAt.
  4. Prefix set-once: prefix đã nằm trong parts[0]; sau commit đầu tiên set s.prefix = '' để phần carry không bị lặp prefix. Ghi chú JSDoc.

Hệ quả: live-edit vẫn áp dụng cho phần đuôi đang chạy; phần đã đầy được "đóng băng" thành tin riêng. Không mất ký tự.

D2 — AskUserQuestion render (tool-render)

  • Bỏ hard-cut ASK_BODY_MAX (hoặc nâng lên rất cao chỉ như safety-net chống pathological, vd 16000). Giữ sanity cap mềm cho từng field nhưng KHÔNG cắt mid-word phần người dùng cần đọc — ưu tiên render full label + full description.
  • Vì việc chống tràn 4096 chuyển sang tầng gửi (D3), render không cần tự ép 3500 nữa.

D3 — AskUserQuestion gửi qua sendChunked (commands dispatch)

  • Khi e.tool === 'AskUserQuestion': bypass burst-collapse (AskUserQuestion không bao giờ là burst), gửi bằng notifier.sendChunked(formatted, { silent }) thay vì sendPlain.
  • pending-tools registration: giữ tương thích — dùng message_id đầu tiên trả về từ sendChunked.

D4 — sendMarkdownV2 chunk + re-fence (code blocks)

  • Thêm sendMarkdownV2Chunked(): split theo line-boundary, mỗi chunk re-wrap fence ``` hợp lệ (đóng cuối chunk N, mở đầu chunk N+1). Path code-block (commands ≈1401) dùng hàm này.
  • Fallback parse-error giữ nguyên: nếu MarkdownV2 fail → plain (đã chunk).

Findings (with fixes applied)

  • [P1] code-block first-chunk fence chop. CODE_CHUNK_BUDGET was 3500 — exactly sendMarkdownV2's internal clip(3500) threshold. The dispatch prepends escapeMd("[label] ")+"\n" to chunk[0], pushing the composed first message to ~3506 chars → clip() chopped the closing ``` → MarkdownV2 parse error → plain fallback with lost tail + stray "…". Fix: CODE_CHUNK_BUDGET = 3500 − 96 headroom for the prefix. Regression test added (chunk[0]+long-label ≤ 3500, fence intact).
  • [P2] hard-split worst-case escape overflow. Single-line hard-split used floor(BUDGET/2) raw chars, ignoring the fence wrapper. An all-backslash/backtick line escaped 2× → 3512-char chunk (> budget, still < 4096 so no Telegram reject). Fix: HARD_SLICE = floor((BUDGET − WRAPPER)/2); verified worst-case chunk ≤ budget. Regression test added (pure-backslash + pure-backtick lines, with/without lang).
  • [P3] inter-chunk newline cosmetics. splitForTelegram drops the join \n at part boundaries (existing shared-infra contract). In the flush rotation, two paragraphs split across messages lose the boundary newline — invisible across separate Telegram bubbles, matches spec Q1's accepted "seamless prose" answer. Not patched (out of scope; would alter shared infra).
  • [P2 — out of scope, flagged not patched] AskUserQuestion suppressed in summary mode. shouldEmit() drops tool_use in the default summary mode, so an AskUserQuestion never reaches the new dispatch branch unless the session is in normal/thinking/verbose. This is pre-existing behavior unrelated to truncation; surfacing blocking asks regardless of mode is a separate feature decision. Recommend a follow-up spec.
  • [P3] stale comment. Dispatch comment referenced removed maybeWrapCodeBlock; updated to describe detectCodeBlock/wrapCodeBlockChunked.

Concurrency / state-machine

The flush() rotation is non-transactional (commit loop runs before s.buffer shrinks; a mid-loop throw bubbles to handleSendError retry which re-runs from the full buffer → possible duplicate head chunk on a transient 429). This is the SAME risk the original clip() code carried and is documented in-code; takeToken() pre-waits the rate limit so mid-loop 429s are rare. Judged acceptable for the bug-fix scope. Prefix set-once mutation (s.prefix='' after first commit) verified: no double-emit — subsequent flushes compose from buffer only; re-overflow re-splits with already-blank prefix.

AskUserQuestion dispatch wiring

Bypassing pending.addPending does NOT orphan a tool_result: the matching tool_result hits the existing orphan branch (fresh sendPlain of the ✅/❌ marker) — no keyboard flow exists for AskUserQuestion (answered via free-text reply), so nothing breaks. labelPrefix + fallbackLine = "[label] 🔧 …", matching the collapse format ordering.
